# Fix Test Suites

Diagnose and fix failures, errors, and warnings that show up in the structured test results (`index.json`) of **two or more `datrix-*` packages** at once, treating them as one problem set. Use it when a change in one package breaks tests in others, or when the same root cause surfaces in several runs. For a single package use that package's `/fix-*` skill.

**Execute the shared playbook:** read `d:\datrix\.claude\skills\_shared\fix-package-playbook.md` and follow it, with the multi-package adjustments below. The playbook owns the index.json schema, the extraction scripts, the per-cluster investigation steps, the security and no-expedient-fix rules, and the abort conditions. This file only changes what the playbook scopes to one package.

## How to Invoke

```
/fix-test-suites D:\datrix\datrix-common\.test_results\test-results-YYYYMMDD-HHMMSS\index.json D:\datrix\datrix-codegen-kernel\.test_results\test-results-YYYYMMDD-HHMMSS\index.json
```

The arguments are one or more absolute paths to an `index.json` inside a `.test_results/test-results-*/` directory, each from a different repo (two runs of the same repo are allowed; the newer one wins for that repo, and say so). Separate them with spaces, commas or new lines.

## Parameters

- `{RUNS}` = the supplied index.json files. For each, `{PACKAGE}` is the `project` field of the file and `{PACKAGE_PATH}` is `d:\datrix\{PACKAGE}\`.
- `{SCOPE}` = the set of `{PACKAGE}` values across `{RUNS}`. **This set is the fence for the whole job.**

Reject at once, naming the file, any path that does not exist, is not an `index.json`, or whose `project` does not resolve to a directory under `d:\datrix\`.

## Multi-package adjustments to the playbook

The playbook's single-repo scope is a standing order for `/fix-{suffix}` skills. Jon's invoking `/fix-test-suites` with several runs lifts it for the repos in `{SCOPE}`, and only for them:

- **Read, edit, and run tests in any package in `{SCOPE}`.** Never touch a package outside it.
- **Tests:** `-Specific` and `-Tag` runs only, at most 3 tags per run, `-Keyword` in one package only. Never a whole suite, a tier switch, `-All`, `-Rerun`, or `affected-gate.ps1`. A package outside `{SCOPE}` is never named in a `test.ps1` call.
- **Root cause in another package of `{SCOPE}`** → fix it there, in the same job. This replaces the playbook's "Cross-Project Root Cause" stop for in-scope packages.
- **Root cause outside `{SCOPE}`** → do not fix it and do not write a findings file for it. Stop work on the clusters traced there and state, under `Unresolved`, the package, `file:line`, the evidence and the cluster IDs. Jon decides whether to add that package's run.
- **Findings** for a defect inside `{SCOPE}` that the fixes do not need still go to `d:\datrix\findings\` per the CLAUDE.md rule.

## Scripts and local models first

Spend your own tokens on judgment and edits; let scripts and the local model do the reading. Use them in this order, and treat every local-model answer as a lead you confirm with a ranged Read before editing:

- **Run triage:** `digest.txt` and `failure-data.json` (written by `test.ps1`; its per-family `hint` is a local model's reading) before any other file. `collect-failure-data.ps1` and `extract-warnings.ps1` only when they are absent. Never hand-parse `index.json`, `failures/` or `full.log`.
- **Logs:** a test, generation or deploy log you must read goes through `digest_log` (`datrix-local-llm`), not a whole-file read.
- **What code does:** a large file you would read whole to learn how something works goes through `ask_files` (`datrix-local-llm`). Never use it for definitions or call sites, which a model invents.
- **Definitions and uses:** `find_canonical`, `find_symbol`, `find_references`, `outline`, `search` (code-index MCP); without the MCP, `datrix/scripts/dev/code-index.ps1`. This is also how you prove a shared root cause: the same symbol referenced from the frames of several runs.
- **Where is it documented:** `datrix/scripts/dev/ineedtoknow.ps1 "<question>"` before opening docs.
- **Package layout:** `{PACKAGE_PATH}.project-structure.md`, regenerated by `workspace/project-structure.ps1` when missing, never a directory walk.
- **Tags:** `test.ps1 <package> -ListTags` (runs nothing) to choose the tags of a changed behaviour.
- **Fallback:** when an MCP server is unavailable, say so in one line and use the script twin or a ranged Read. Do not stop.

## Workflow

### Step 1: Load every run

For each index.json, follow playbook Step 1 unchanged: read `digest.txt` and `failure-data.json` from its run directory when present, run `collect-failure-data.ps1` only when `failure-data.json` is absent, and run `extract-warnings.ps1` when `warnings_section_present` is true. Do not read `failures/` or `errors/` files for triage.

Then store the job's finish line: `test/failure-ledger.ps1 -Runs <the index.json paths, comma-separated>`. It lists the failing test ids by package; `-Status` at any point shows which are still open. The job is not a pin count or a green file: it is finished only when `-Status` prints `LEDGER: 0 open id(s)`.

### Step 2: Correlate across runs, then order the work

Build one table of families across all runs: `run (package) | family label | normalized pattern | source_location | cluster IDs`. Then group:

1. **Shared root cause.** Families in different runs that share a pattern, a missing or renamed symbol, a changed signature, or a traceback frame in the same upstream module are one defect until the evidence says otherwise. Trace the shared one to its source once. Compare the frames, not the wording.
2. **Dependency order.** Fix upstream packages before downstream ones: `datrix-common` → `datrix-rdbms-schema` / `datrix-semantic` → `datrix-language` / `datrix-codegen-kernel` → `datrix-codegen-common` / `datrix-codegen-typescript-core` → the generators → `datrix-cli`; `datrix-testing` and `datrix-extensions` by what the traceback names. A downstream failure caused by an upstream defect is closed by the upstream fix, not by a downstream change. Confirm the direction in the architecture cheat sheet's package table when the order is not obvious.
3. **Errors before failures before warnings**, within each package, as in the playbook.

**More than 5 distinct root causes (after merging shared ones) → STOP and propose a split**, listing the root causes and the runs each one covers. Many families that resolve to few root causes is not a reason to stop.

### Step 3: Fix

Per root cause, in the Step 2 order, run playbook Steps 3–7: read the test, trace to the source module, decide source bug vs outdated expectation vs wrong setup, apply the correct fix, and verify with `test-single.ps1` on the originally failing tests (`-Project` set to the package each test lives in).

- **Read before you write.** A fixture project's `.dcfg` keys, flavors and DSL shapes come from the schema and a sibling fixture that already analyzes, not from memory. After writing or editing a fixture project, run `dev/probe-fixture.ps1 -Path <project>` (it prints the real error in seconds); `guard-test-run-discipline.py` refuses the suite run until you have.
- **One command per test run.** Do not chain an edit or a check onto a test run; the hook refuses it.
- **Rewriting existing tests is sized first.** Past 25 test files in a session the edit is refused until the decision advisor has been consulted; converting more tests than the failures need is scope growth.

### Step 4: Warnings

After the errors and failures of all runs, playbook Step 8 per run.

### Step 5: Final check, per package

Playbook Step 9, once, after every fix: for each package in `{SCOPE}`, re-run its originally failing tests plus the test files you added or edited (`-Specific`), then the feature tags of the behaviours you changed in that package (`-Tag`, at most 3 per run). A changed behaviour no tagged test covers gets a new tagged test in the package that owns it.

Then `test/failure-ledger.ps1 -Status`: every open id is work (`FAILING` = still red, `NOT-RERUN` = not yet proven, `NEW` = a failure the starting runs never had, so a regression or an unreached test). A failed run writes a new `.test_results/` directory: work every cluster it reports. The turn ends when `-Status` prints `0 open id(s)` and every changed behaviour's tags pass in every package of `{SCOPE}`, or at a valid B1–B4 blocker with its four-part proof.

### Step 6: Report

```
FIX-TEST-SUITES COMPLETE
Runs: {package: index.json path} (one line each)
Original issues: {E} errors, {F} failures in {C} clusters, {W} warnings — {R} distinct root causes
Root cause {n}: {file:line in package} — {what was wrong} — covers {package: cluster #ids}
Fixed: {file:line} — {what changed} — {package / cluster #id / warning category}   (one line each)
Verification: per package — originally-failing tests {PASS/FAIL}; warnings resolved {N}/{total}; tags {list} {PASS/FAIL} ({pass}/{total})
Reaches (not run): {packages outside SCOPE and tags the change touches, or "none"}
Unresolved (if any): {package: cluster/warning} — {reason; for a cause outside SCOPE: package, file:line, evidence}
```

## Anti-Patterns

All playbook anti-patterns apply, with the cross-package ones narrowed to `{SCOPE}`. Plus:

- **NO fixing the same defect once per run** — a shared root cause gets one fix at its source, and the downstream clusters are verified, not patched.
- **NO symptom patches downstream** — a test in a downstream package that fails because of an upstream defect is never "fixed" by loosening the downstream test or adding a guard.
- **NO packages outside `{SCOPE}`** — no edits, no tests, no findings files; they go in `Unresolved` or `Reaches (not run)`.
- **NO sweeps assembled from several `-Tag` calls** to dodge the per-run limits; a tag set that is too broad means the tags are wrong.
