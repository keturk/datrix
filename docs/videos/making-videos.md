# Making Videos with the Video Skills

How to make narrated videos of an application generated by Datrix (a demo, an app tour, or a walkthrough from the
spec to the generated code) with Claude Code and the video skills. The videos have no presenter and no microphone:
Claude drives real browser windows at a human pace, OBS records the screen, an AI voice (Kokoro) reads the narration,
and every finished video is checked before it is handed over. The same skills make Datrix's own videos for YouTube,
using the examples under [`examples/`](../../examples/).

## What the skills are for

### Three kinds of video

| Kind | What it shows | Uses up data? |
| --- | --- | --- |
| **Story** | One realistic flow across apps and personas: someone acts, someone approves, the effect shows up elsewhere | Yes: each take consumes inputs (an order to ship, a customer's first payment) |
| **App tour** | One app, one stop per page in menu order, the pointer resting on what the narration names | No: read-only, can be recorded again at any time |
| **Code walkthrough** | One concept followed from the `.dtrx` spec to the files generated from it, ending on the running app | No |

### The seven skills

The skills are installed per user under `~/.claude/skills/` (they are not part of this repository), so they are
available in every Claude Code session on that PC, in any folder.

| Skill | Does |
| --- | --- |
| `video-production` | The entry point: knows the whole pipeline and hands each stage to the skill that owns it |
| `video-survey` | Opens every page as every persona and notes what works, what is empty, what is slow and what is broken |
| `video-script` | Writes the video module (cards, segments, narration) and the script doc people read |
| `video-record` | One-time PC setup, generating the narration, rehearsing, and recording a take |
| `video-finish` | Turns a take into the finished video and proves it with checks; diagnoses a problem someone reports |
| `video-code-walkthrough` | The extra steps for a spec-to-code video |
| `video-publish` | File names, descriptions, and a YouTube upload kit |

`video-production` also holds the engine (`engine/`, Node scripts) and the templates for a new project (`templates/`).

### What you get

For each video, side by side in the project's final folder:

- the video, `NN-<name>.mp4` (1920×1080, 30 fps), numbered in viewing order;
- captions: `.srt` for upload, `.vtt` for a web page;
- a poster image, `.jpg` (the title card, 1280 px wide).

A video counts as done only when the finisher prints `Done.`: every narration line is where its caption says, as loud
as its source file, and heard whole by a speech recogniser (Whisper).

## Quick start

You do not run the skills by name. Ask Claude Code for a video in plain words and it loads `video-production`, which
loads each stage's skill when it reaches that stage. Typing `/video-production` works too.

Example requests:

- "Make an app tour of the ecommerce example's admin app."
- "Make a demo video of an order, from the storefront to the admin app."
- "Make a code walkthrough of what the `Order` entity in the ecommerce example generates."
- "Something is wrong at 1:35 in 02-admin-app.mp4: the voice stops, then it's garbled."
- "Prepare 03 for YouTube."

Tell Claude three things up front and it will not need to ask:

1. **Which application**, and where it runs (a staging server, a local run).
2. **Which kind of video**, and who it is for (a prospect's decision makers, developers on YouTube).
3. **Anything off limits**: a shared system, another product on the same server, data that must not change.

What you will be asked for along the way:

- **Approval before a shared system changes.** A story video uses up data, and fixing broken data on a shared system
  needs your say-so. Claude names the exact rows and the alternative.
- **Approval before anything leaves the PC.** Uploading, sharing a link or posting is always your call.
- **A listen.** The finisher lists narration lines where the voice may have mispronounced something (abbreviations,
  unusual names and Latin terms are the usual ones). You decide whether a line needs rewording.
- **Hands off during a take.** Do not touch the mouse or the windows while a take is recording.

## One-time setup of a PC

Ask Claude to "set up this PC for video recording". It follows the `video-record` skill; you do the steps that need
your hands or your password.

1. **Install the tools**: Google Chrome, OBS Studio 30 or later, and FFmpeg (`winget install Gyan.FFmpeg`; on ARM64
   Windows this is the build that works, the npm FFmpeg packages have no ARM64 binary).
2. **Install the engine's packages**: `npm install` in `~/.claude/skills/video-production/engine`. The versions are
   pinned.
3. **Configure OBS**:
   - a scene with a **Display Capture** of the display you will record;
   - Settings → Video: base and output resolution 1920×1080, **30 fps** (integer);
   - Settings → Output: recording format mp4;
   - Tools → WebSocket Server Settings: enabled, with a password.
4. **Store the OBS password, encrypted.** In PowerShell, run this and type the password when it waits:

   ```powershell
   Read-Host -AsSecureString | ConvertFrom-SecureString | Set-Content ~/.claude/video-production/obs-websocket.dpapi
   ```

   Only your Windows account can decrypt the file. The password is never written in plain text anywhere.
5. **Run or point at a voice server and a checker server**: a Kokoro-FastAPI server (text to speech) and an
   openai-whisper-asr-webservice server (speech to text). Neither has authentication, so publish each on
   loopback only, and give a GPU image the GPU (without `--gpus all` it runs on the CPU):

   ```bash
   docker run -d --name kokoro --gpus all -p 127.0.0.1:8880:8880 ghcr.io/remsky/kokoro-fastapi-gpu:<tag>
   ```

   When they run on another machine, reach them through an SSH tunnel rather than a port open to the network:
   `ssh -N -L 8880:127.0.0.1:8880 -L 9000:127.0.0.1:9000 <user>@<server>`, and point the settings below at
   `http://127.0.0.1:8880` and `http://127.0.0.1:9000`.
6. **Write the machine settings**, `~/.claude/video-production/settings.json`:

   ```json
   { "chrome": "C:/Program Files/Google/Chrome/Application/chrome.exe",
     "ffmpeg": "<FFmpeg folder>/bin/ffmpeg.exe", "ffprobe": "<FFmpeg folder>/bin/ffprobe.exe",
     "display": "<left>,<top>,1920,1080",
     "obs": { "url": "ws://127.0.0.1:4455", "passwordFile": "obs-websocket.dpapi" },
     "tts": { "url": "http://127.0.0.1:8880" }, "stt": { "url": "http://127.0.0.1:9000" } }
   ```

   `display` is the recorded display's left, top, width and height in Windows' virtual desktop. A display left of or
   above the main one has negative coordinates, for example `2304,-621,1920,1080`. `VIDEO_DISPLAY` overrides it for
   one run.

The recorder mutes OBS's microphone and desktop audio during a take and restores them afterwards; the recorded clips'
own sound is never used.

## Starting a new video project

One engine makes every video. What is specific to one application lives in its own **video project** folder, usually
beside the application (for example `.video/` in the application's folder). Claude starts a project by copying
`video-production/templates/` and filling it in.

```
<project>/
  video.config.js      the application: apps, personas, where secrets live, the videos
  videos/<name>.js     one module per video
  narration/           voice files (written by the engine)
  recordings/          takes, one folder per take (written by the engine)
  build/               cards, code pages, segment timings (written by the engine)
  final/               finished videos, unless video.config.js points elsewhere
```

### What goes in video.config.js

| Field | What it holds |
| --- | --- |
| `name`, `voice`, `note` | The product's name, the Kokoro voice (for example `af_heart`, `am_michael`, `bm_george`), and the small print on the cards: where it was recorded and what is simulated |
| `roles` | One browser window per persona: the app's address, how it signs in (`zitadel`, `grafana` or `none`), the login, and which secret holds the password |
| `secrets` | Where each password lives, never the password itself: a git-ignored PowerShell data file (`psd1`), a key in a server's `.env` read over SSH (`ssh-env`), a DPAPI-encrypted file (`dpapi`), or an environment variable (`env`) |
| `api` | The API address, for set-up calls a story makes off camera (optional) |
| `brand`, `label` | Fonts and colours for the cards; a label shown over every shot of certain apps, such as "Simulated provider" (optional) |
| `code` | Syntax grammars for code walkthroughs; the `.dtrx` grammar ships with Datrix's VS Code extension (`datrix-vscode/syntaxes/dtrx.tmLanguage.json`) (optional) |
| `final` | Where finished videos go (optional) |
| `videos` | Each video's module and its finished file name, numbered in viewing order (`01-…`, `02-…`) |

The templates hold a tour, a story and a code walkthrough module to start from.

## Making a video, stage by stage

Every video goes through the same five stages, in order. Claude runs them; this is what happens at each.

### 1. Survey (`video-survey`)

Claude signs in as every persona and opens every page the video might show. Each page gets a verdict: **show**,
**empty — leave out**, **slow — open off camera**, or **broken — fix or leave out**. The verdicts go into the
project's script doc as a known-issues table. A broken page is never filmed: it is fixed first (with your approval
when that means changing a shared system), or left out. A defect of the generator is reported to Datrix.

### 2. Script (`video-script`)

Claude writes the video module: a title card, the segments and a closing card. Each segment says whose window is on
screen, what happens off camera to get ready, what the viewer sees happen, and the narration for it. Narration
follows a few rules:

- One idea per segment, about 6 to 12 seconds spoken, in the present tense, describing what is on screen.
- Things are named the way the screen names them, in plain words.
- Every claim is checked against the running app or the code, never against a document's description of it.
- Figures on the cards come from where they are counted.

A story's inputs (the customer, the product, the amount) are listed in the module's `data`, with the values earlier
takes used noted beside them, so each take picks unused ones. Claude also writes the script doc: purpose, audience,
a table of segments, the inputs a take uses, and the known issues.

### 3. Record (`video-record`)

1. **Narrate.** Kokoro turns every line into a voice file. Change a line, and only that line is narrated again.
2. **Rehearse.** The recorder runs every segment with OBS off. Every failure is fixed before recording: a selector, a
   slow page that belongs off camera, or a real defect that goes back to the survey.
3. **Record.** The recorder signs everyone in off camera, shows each segment's window full screen on the recorded
   display, and records **one silent clip per segment** into a new take folder. A story step that fails at random (a
   simulated provider that sometimes skips a step) makes the recorder record the whole take again with the next
   inputs, up to three times.

### 4. Finish (`video-finish`)

The finisher joins the clips, lays each narration file in exactly where its segment starts, adds the title and
closing cards and any label, and writes the captions and the poster. It prints `Done.` only when all of these hold:

- every narration is within 0.1 s of where its caption says, and within 1 dB of its file's loudness;
- Whisper hears at least 85% of every line's words, in order, in the finished file;
- picture and sound are the same length, to the frame, and the whole is as long as planned.

Claude then looks at a frame from the middle of every segment, and checks the lines the finisher asks someone to
listen to.

### 5. Publish (`video-publish`)

Finished files are numbered in viewing order and placed where they will be played from. Claude writes a short
description of each video and, for YouTube, the upload kit below. Nothing is uploaded or shared without your
approval.

## Code walkthrough videos

The viewer sees the spec on the left and the generated files on the right, one chapter per part of the spec, with the
pointer on the lines the narration names. The engine builds these pages from the files as they are on disk: the video
module names each file and the lines to show (from one line to another, a number of brace blocks, or every line that
matches), never a pasted copy. If the code changes so that a named line no longer exists, the build stops instead of
showing stale code.

- **Choose one concept, small in the spec and large in what it generates**: an entity with a few fields, an endpoint
  with its roles, a page with a form. Two to four chapters, about twelve stops, about two minutes.
- **End on the running app**, so the walkthrough closes the loop from spec to product, then a page of counted
  figures: lines of spec, files generated for the concept, and lines in those files. Files that also hold other
  things (the database schema, the routes, the API client) are tagged as shared and left out of the counts.
- **Every generated file is read before it is shown**, and every claim checked against it. A generated file that is
  wrong is reported to Datrix and replaced by another file or subject; a defect is never narrated as a feature.
- **Review the pages before recording**: `pages.js --shots <folder>` builds every page and screenshots it.

For Datrix's channel the subject is one of the examples, for instance the `Order` entity of
[`examples/03-domains/ecommerce`](../../examples/03-domains/ecommerce/), generated for one language and platform; the
title card says which. A series can show the same spec generated for two targets, one video each.

## When something is wrong in a finished video

Tell Claude the video and the time ("at 1:35 the voice cuts out"). It works the problem the same way every time:

1. **Turn the time into a line.** `build/<video>/segments.json`, written by the finisher, says which segment plays at
   that second.
2. **Reproduce before changing anything.** Frames around that second for a picture problem; for a voice problem,
   `voicecheck.js` hears every line of the finished file again and reports which lost words; a damaged line is then
   compared with its narration file and its clip, to find which one lost it.
3. **Fix the cause where it is**: the engine (with a check that would have caught it), the video module, the
   narration, or the application. Then record or finish again, and every check runs again.
4. **Replace the published files together** (`.mp4`, `.srt`, `.vtt`, `.jpg`); a web page plays them by name.

## Publishing and YouTube

For a YouTube upload, Claude prepares a file beside the video (`NN-<name>.youtube.md`) for you to upload from or
approve:

- **Title**: what the viewer gets, under 70 characters, product name included ("From spec to code: one entity in
  Datrix").
- **Description**: a short paragraph from the video's own narration and cards; then **chapters** (`M:SS Title`, the
  first at `0:00`, at least three, each at least 10 s long) built from the segment starts the finisher recorded; then
  where to learn more, and the note from the title card (where it was recorded, what is simulated).
- **Captions**: the `.srt`, which is the exact script, not an automatic transcript.
- **Thumbnail**: the `.jpg`, the title card at 1280 px wide.
- **Visibility**: yours to decide; private until you say otherwise.
- **Playlist**: for a series, in the `NN` order.

For a web page, the video, its poster and its caption track go together:

```html
<video controls preload="metadata" poster="videos/02-admin-app.jpg">
  <source src="videos/02-admin-app.mp4" type="video/mp4">
  <track kind="captions" src="videos/02-admin-app.vtt" srclang="en" label="English" default>
</video>
```

## Rules the skills follow

- **Every claim in a narration is true of what is on screen**, checked against the running app or the code.
- **Nothing fake that could pass as real.** Personas and data are fictional, and the cards say where the video was
  recorded and what is simulated.
- **Secrets are read where they live, for the run, and never printed.** The project names where each one lives; a new
  secret goes into its owner's store, never into a project file.
- **Shared systems are not changed without approval.** That covers data, servers and releases.
- **A defect found on the way is not hidden by the video.** It is fixed (with approval when it needs it), or left out
  of the video and reported.
- **A reported problem is reproduced before anything changes**, and the video is checked again after the fix.

## Reference

Every engine command takes `--project <project folder> --video <name>` (except `frames.js`) and runs as
`node ~/.claude/skills/video-production/engine/<command>.js …`.

| Command | Does |
| --- | --- |
| `narrate.js [--voice v] [--only ids] [--speed s]` | The narration voice files and their lengths, in `narration/<video>/<voice>/` |
| `record.js [--no-obs] [--only ids] [--from id]` | Drives the apps; without `--no-obs`, records one clip per segment into `recordings/<date time> <video>/` |
| `finish.js --take <take folder> [--out file.mp4]` | The finished video with `.srt`, `.vtt` and `.jpg`, and every check |
| `voicecheck.js --file <finished.mp4>` | Hears every line of a finished video again (an audit) |
| `pages.js [--shots folder]` | Builds a code walkthrough's pages, and screenshots them for review |
| `frames.js --file f --at 8,36 --out folder` | PNG frames of any video at the given seconds |

Why one silent clip per segment: an earlier design paused one OBS recording between segments and played each
narration live through OBS. Live playback sometimes lost the start of a line, and OBS's recording clock drifted from
the file by over a second, which misplaced the voice. Clips have exact lengths, and laying the narration in from its
files afterwards keeps every line whole and in place.
