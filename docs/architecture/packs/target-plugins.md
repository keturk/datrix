**Read when:** adding or changing a language/platform/frontend target, a plugin entry point, a capability declaration, identity-provider/flavor/runtime validation, a package dependency edge, an import boundary, or a domain extension.

## Multi-Target Plugin Architecture

Open-world targets, derived conformance: [Decision 15](../architecture-overview.md#decision-15-multi-target-plugin-architecture--open-world-targets-derived-conformance-adopted) — Adopted.

(The check commands are `powershell -File "d:/datrix/datrix/scripts/scan/check-import-boundaries.ps1" <flag>`.)

**A service's language is resolved per service.** A service `.dcfg` may declare `language = "<id>"`. `service_languages_for(app, default_language)` (`datrix_common.config.codegen_context`) validates it against the registered `datrix.languages` set with `resolve_language_id` (`plugin_registry().language_plugin_names()`, so a generator that is no language, such as `sql`, is refused). A service that declares no language takes the run's `--language` default. Each answer is logged as `service_language_resolved service=… language=… source=dcfg|cli` and held in `CodegenContext.service_languages`; there is no run-wide language field. A system `.dcfg` refuses the key. A system is generated in one language: `service_languages_for` refuses services that resolve to two or more, naming the services of each. Everything downstream asks per service or per set: `context.language_of(service)` for one service, `context.languages()` for the run's set. Examples: companion activation (`PluginDescriptor.is_active_for(app, languages)`), the language plugins `discover_generators` loads, pre- and post-write language hooks (each owns the files of its own services' trees), and the shared container base images (one per language, `resolve_shared_base_images`).

**One plugin registry per process.** Plugin classes and instances are discovered once per process, into the registry `datrix_common.plugin.registry` owns: production code reads it through `plugin_registry()` (`from datrix_common.plugin.registry import plugin_registry`), which returns the module global `_PROCESS_REGISTRY` at call time, and never constructs `PluginRegistry` itself. A construction rescans every installed distribution's entry points and builds an instance a test swap cannot reach, so no module holds a registry of its own, bound at import or built per call; a function taking `registry: PluginRegistry | None = None` defaults to `plugin_registry()`. Sharing the instance is safe: everything it caches is a declaration, and the extension packs keep no instance state. Tests swap the one registry with `monkeypatch.setattr(registry_module, "_PROCESS_REGISTRY", fresh)` and every module sees the swap; only the test harness (`datrix_testing`, `datrix_codegen_common.testkit`) builds fresh registries. The repo tooling under `datrix/scripts/**/lib/` follows the same rule; a gate self-test that needs fixture plugins installs them through `datrix_testing.conformance.plugin_harness.process_fixture_plugin_environment` rather than building a registry. Held by the ast-grep rule `ad-hoc-plugin-registry` (`powershell -File "d:/datrix/datrix/scripts/scan/ast-grep.ps1" <packages> datrix -Rule ad-hoc-plugin-registry`, zero findings over every package's `src/` and the showcase's `scripts/**/lib/`).

**Type maps are plugin values; the type-mapping registry is built per run.** A language plugin declares its own map as `LanguagePlugin.static_type_map` (`Mapping[str, TypeMappingBase]`: the core table merged with every extension's entries by `datrix_codegen_kernel.generation.type_mapping_registry.static_type_map`), and a client target declares the same on its `PluginDescriptor.static_type_map`, required with the rest of the client-target bundle (`validate_client_target_declarations` refuses a client target without one). Importing a module registers nothing: no process-wide `TypeMappingRegistry` exists. The CLI's discover-generators stage discovers one language plugin per language the run generates a service in, and builds the run's registry with the kernel's `datrix_codegen_kernel.generation.discovery.run_type_mapping_registry(language_plugins, companions)` — `TypeMappingRegistry.from_maps({descriptor name: map})` over every language plugin and client-target companion, seeded with every canonical type name so a gap every target shares stays visible, refusing two plugins of one name — and stores it under the `TYPE_MAPPING_REGISTRY` artifact key; the type-completeness stage reads it there, checks each language over the types its own services, the modules and the shared blocks use, and refuses a registry with no map for a language of the run. A test or gate builds its own registry from the plugin it holds (`check_type_map_exhaustive`, the parity gate's `type_mapping_completeness`), so two registries in one process never see each other's entries.

**Plugins hand registries to the run as values; importing a module registers nothing.** A registry filled as a side effect of an import answers differently depending on what was imported first, so every registry a run reads is built from values its owners declare. The builtin definitions are one example: `datrix_common.builtins.objects.BUILTIN_OBJECTS` is the declared tuple of every core `Builtin` subclass, an extension hands its own over as the classes its `builtin_objects()` returns, and `datrix_common.builtins.definitions.builtin_definitions()` keys both by declared name (refusing a name declared twice, or an extension entry keyed under another name). `BuiltinMeta` only checks that a definition's `name=` and `description=` keywords are strings; defining or importing a class makes nothing visible. Held by `datrix/scripts/gates/repo-hygiene/no-import-registration-gate.ps1` (zero hits over every `datrix-*/src`: no call statement that runs on import with `register` in its callee name, no `# noqa: F401` import kept for registration).

**A new target's declarative cases register from its own `tests/`.** The case format, runner and registries (`datrix_testing.cases`) name no target. A new language, platform or frontend covers its facts as case rows by registering, from its own `tests/conftest.py`, what only it has: a stage (`register_stage`), an observer (`register_observer`), the parser family of an artifact kind no shipped family reads (`register_surface_family`) and its typed builders (`register_builder`). A registration is visible in that package's session only; no edit to `datrix-testing`, the runner or the case schema is ever needed. `cases.ps1 check` names the package registering a stage or observer a case uses when the case's own package does not ([unit-test-guidelines §4](../../../../datrix-common/docs/contributing/test-guidelines/unit-test-guidelines.md#decision-facts-as-cases)).

**A new target's tables register from its own `tests/` too.** The table-contract runner and registry (`datrix_testing.tables`) name no table, language or target. A new target registers, from its `tests/conftest.py` with `register_table`, the contracts of the tables it owns and the per-target contracts it is obligated to, built from its own facts: its DAL generator file declarations (`datrix_testing.conformance.dgen_files.dgen_file_contracts(<its import root>)`, which finds the targets whose definitions the package ships), and for a language or client target its cell of the builtin matrix (`BuiltinTarget`: name, axis, capability declaration, mapper, parser family, call-site values; a client target builds it with `client_builtin_target(<its plugin descriptor>, <its parser>)`), its emit tables and its type map (`datrix_codegen_common.testkit.tables`). Each table registers where it lives: a language core that is its own package registers its emit tables and type map, and the backend owning the capability declaration registers only the matrix cell. The completeness gate proves it did: a language passes `session_registry().tables()` to `run_all_language_completeness_gates`, a client target calls `check_builtin_matrix_cell_registered(<its descriptor name>, session_registry().tables())`, and a target with no matrix cell fails by name. It carries the one runner module `tests/test_tables.py`; every row is then an item `test_table[<table>::<row>]`, and a builtin the target neither realizes nor gap-rows is one named failure in its own suite ([unit-test-guidelines, Table rows](../../../../datrix-common/docs/contributing/test-guidelines/unit-test-guidelines.md#table-rows)).

## Open-World Identity, Flavors, Runtimes

[Decision 22](../architecture-overview.md#decision-22-open-world-identity-providers-and-infrastructure-flavors-adopted) — Adopted.

Identity provider types, the six infrastructure flavors (Rdbms/Cache/Pubsub/Queue/Nosql/Storage) and deployment runtimes are **open identifiers validated against the installed platform plugins** — no central capability matrix, no closed enums. Each platform declares its own column (identity `(provider type, feature)`, flavor cells, runtime support, identity write-back claim/encoding) in its `PlatformCapabilityDeclaration`. An unknown value fails loud, listing what the installed plugins declare. A platform declaring no write-back realization fails loud on write-back.

**Identity provider rules have one owner.** What a provider type's issuer, JWKS and audience are is a fact about the provider product, not the platform hosting it, so the rules live in the package that integrates the provider (docker → `zitadel`, aws → `cognito`, azure → `entra-id` / `entra-external-id`; `external` is built in) and are registered on that package's `PlatformCapabilityDeclaration.identity_provider_type_rules`. The `.dcfg` vocabulary is open-world the same way: `IdentityConfig.provider` names only the built-in `external` and `apiKey` types, and a contributed type's provider-specific block (its key and model, `source_block`) and whether Datrix hosts its issuer (`self_hosted`, which licenses `mode = self`) are the owner's rules too, checked at the identity-config load boundary. A platform that only realizes a type owns nothing. The shared planner asks the registry; the deploy-time identity context is an open map keyed by provider type and built by one reader from each platform's declared projection.

## Foundation Package Restructure

[Decision 50](../architecture-overview.md#decision-50-foundation-package-restructure--smaller-shared-packages-narrower-change-reach-adopted) — Adopted.

Change reach is computed per package, so the shared layers split into the packages in the core map. Invariants: no upward import from a lower layer, `TYPE_CHECKING` included (import-linter `layers` contract per package, zero ignored edges; manifest-import parity gate); importing the core loads no generation, migration or semantic code; the kernel loads no language-layer module; platforms, SQL and component never depend on the language layer; no frontend target depends on a backend language package; every shared package is covered by the shared-layer ratchets (derived set, an unclassified package fails the scan); **exactly one import path per symbol** (`check-import-boundaries.ps1 -CheckReexportFacades`, standing hard zero, no baseline). A module is placed by who uses it: the nearest package every consumer already depends on; a pure derivation over the model lives beside the model; a module holding a core fact beside an upper-layer one is split.

## Domain Extensions

- **DSL:** `use extension <name>;` inside `system { }` (stored on `app.extension_directives`).
- **Protocol `DatrixExtension`** (`datrix_common.plugin.extension`): properties `name`, `version`; methods `scalar_definitions()`, `builtin_objects()`, `value_struct_definitions()`, `db_extensions()`, `extra_dependencies()`.
- **Discovery:** `PluginRegistry.discover_extensions()`; `load_declared_extensions(declared)`; `TypeRegistry.load_extensions(extensions)`; `declared_extension_names(app)` is passed into `LanguageGenerator` and resolvers.
- **Split ownership:** packs own definitions; each language/SQL owns its maps — `PYTHON_EXTENSION_MAPS` (`datrix_codegen_python.type_mappings`), `TS_EXTENSION_MAPS` (`datrix_codegen_typescript_core.type_mappings`), `SQL_EXTENSION_MAPS` (`datrix_codegen_kernel.sql_facts.type_mappings`) — merged into the core `*_TYPE_MAP` by the shared `datrix_codegen_kernel.generation.type_mapping_registry.build_type_map` (raises `ExtensionNotSupportedError` for a declared extension with no map). A new language ships its own `*_EXTENSION_MAPS` the same way.
