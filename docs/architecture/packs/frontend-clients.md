# Pack: Frontend Clients and Complete Applications

**Read when:** you touch Angular/Flutter (or any client target), the client or UI contract, the `app` container, generated browser/mobile clients, route manifests, UI diagnostics (`UI0xx`), or web security headers.
**Not for:** backend auth semantics ([auth.md](./auth.md)).
**Core map:** [architecture-cheat-sheet.md](../architecture-cheat-sheet.md)

Decisions [43](../architecture-overview.md#decision-43-frontend-api-client-generation--browser-clients-emitted-from-the-same-dsl-as-the-backend-approved--implementation-in-progress) · [48](../architecture-overview.md#decision-48-complete-applications-in-datrix--web-and-mobile-frontends-from-the-same-dsl-as-the-backend-approved--implementation-in-progress) — Approved, implementation in progress. Decision 48 supersedes Decision 43's statement that components, pages, forms, routing, guards and view-model state are not generated.

- **Two layers:** a framework-neutral **client contract** in `datrix-codegen-kernel` (`generation/client_contract.py`; transpiler-free, also read by the component HTTP contract suite) and a **UI contract** in `datrix-codegen-common`, and one **renderer package per frontend target** (an artifact-phase `datrix.generators` plugin, not a `datrix.languages` plugin). Activation is a declared config fact: the system config's base block names frontend targets as open identifiers validated against installed client-target plugins. The emitted client's language belongs to the target package; `--language` selects the backend only.
- **Client/gateway agreement:** a two-directional set comparison against the shared public-route enumeration; every browser-reachable route is a client method or a counted exemption. Machine-only surfaces (hidden, service, webhook) are never emitted; classification branches on `AuthMode` with a fail-loud default, never on provider-tuple emptiness.
- **Derived, never restated:** wire names, query-param names, pagination parameter names (`offset_pagination_param_names` on `LanguageCapabilityDeclaration`) and handler names come from the backend's plugin and shared helpers. The backend is the language of the services the client calls, `client_backend_language` in `generation/client_contract.py`: the gateway-ingress services are read through `CodegenContext.language_of`, and a service the client does not call never decides it. Called services in two languages fail generation, naming each service and its language. A client that calls no service (a static site) has no backend, so its contract carries no pagination pair and no wire overrides. A UI declaration that restates or loosens a derived fact is an error. No sensitive/hidden field is ever derived or persisted.
- **No secret, token, tenant id, environment URL, or per-profile value in any client file** (byte-identical manifest hashes across profiles). Path parameters are percent-encoded; request-body encoding is decided (multipart for file upload), never assumed; every emitted type is mapped and every referenced type emitted, with no `any` default.
- **The provider manifest is metadata, not authorization.** Never narrow a client per consuming application.
- **Per-service client libraries:** the contract splits into one slice per gateway service and one shared slice (`datrix_codegen_common.generation.client_placement`): a closure type goes to the shared slice when routes of two or more services reach it, to its one service's slice otherwise -- never by its declaring container. The Angular target emits a library per slice, `<service-kebab>-api` and `<system-kebab>-api-common`, named from the declared name without its namespace (a collision fails naming both declarations), each with `src/index.ts`, a `package.json` named `<scope>/<library>` (no `version`), imports across libraries by package name only, and a compile of every library in both generation modes (`tsconfig.libs.json`). Problem decoding (`ProblemDetails`, the exception classes, `callApi`) is HTTP-level and lives in the shared library. Where a target takes settings from an app's own `.dcfg` (`clients { <target> { ... } }`, base-only), it declares them (`ClientTargetCapabilityDeclaration.app_client_settings`, Angular: `scope`); `UI056` refuses an entry outside the app's `targets` or a setting the target does not declare, `UI057` a declared setting no app declares or two apps declare differently. Flutter keeps its own layout.
- **State libraries:** every client target emits, beside its clients, a state library per API, a typed form per write route whose body is one model, and one sample factory per contract type. What is decided is target-neutral and stated once in `datrix_codegen_common.generation.client_state`: which routes hold state (`state_exemption`), each route's handle kind (`state_route_kind`), the entity collections (`answered_entities`, `state_collections`), what a successful write does to the collections (`write_settlement`: remove the id a `DELETE` names, upsert one answered row or many, or nothing -- each target maps every `SettlementKind` to its own call) and which reads it reloads (`reloaded_reads`), a form's body model and whether an update fills from its answer (`write_body_model`, `fills_from_answer`), each member's checks (`member_rules`, `bound_number_literal`), a form's fields at every depth (`form_fields`, walked by `walk_form_fields`: each field's wire path, its kind -- a leaf, a group, a repeatable group or leaf -- its checks, and whether it starts unchecked, is edited as a date-time or is left out while unset), and the state and form censuses (`require_state_census`, `require_form_census`); each target renders them in its own idiom. **Angular:** beside each `<service>-api` the target emits `<service>-api-state`, one classic NgRx feature per client API (actions, reducer, effects, selectors, a facade, `provide<Api>State()`, and a typed reactive form per write route whose body is a model), over one shared runtime `<system>-api-state-common`; `<system>-api-common` stays HTTP-only and no store devtools are emitted. Every route type is read off the generated client class. A feature keeps one entity collection per keyed entity response model (`ClientTypeEntity.key_wire_name`) and per route one request state per consumer key; a facade member is reached through `connect(key)` (a `DestroyRef` lease; the key's state is released with its last lease). Reads switch per key to the newest request and discard stale answers; writes run in order per key; errors are decoded to `ProblemDetails` in the effect so every action and state value is serializable; a successful write reloads every live request of the reads it invalidates: those its `invalidates(read, ...)` declares (`ClientRoute.invalidates`, `API029`; `invalidates([])` reloads none), else every live list over its resource entity (`ClientRoute.resource_entity`). A route answering bytes or taking a multipart body has no plain-data payload and is left to the client, named. Censuses: client methods = facade members = effects; form controls = body fields; one sample factory per contract type. Forms derive validators from the contract's field bounds (`ClientTypeField.constraints`, merged from the type and the `min`/`max`/`minLength`/`maxLength`/`regex` modifiers). Each client library's `<package>/testing` entry point holds `sample<Type>(overrides)` by the shared sample rule (`datrix_codegen_common.generation.ui_test_samples`, also what every target's UI-test `sample(...)` renders; each factory is a `sample_factory_plan`, its sample and required overrides, on every target): a numeric member takes a `min` above its sample, a wire-kind string repeats to its `minLength`, and a member the rule cannot meet (a pattern, a bound its sample breaks, an upload) is a required override. **Generated Angular apps run on these facades:** ui-core holds no request state. Each `data { }` binding and table source is a view (`views.ts`: `singleView`/`listView`, `PageView` with its pager, sizes and sort) over `connect('<Owner>.<binding>#<instance>')` (instance from `uniqueId`, so two instances never share a request); a body's write route goes through a mutation handle's `call(args)` (rejects with `toDomainError`); an app `form` builds its controls with `create<Api><Route>Form()` and disables, without naming, the members it does not show; every app provides the root store through `provideAppStore()` with strict serializability. **Flutter:** `lib/state/<api>_state.dart` per API over the runtime `lib/state/core/` (emitted with the API layer, library-only runs included): `<Api>State` holds the client and one `EntityCollection` per keyed entity response model, and leases one `<Api>Connection` per consumer key (`connect(key)`, `release()`; disposed with the key's last lease) holding one request state per stateful route, named as its client method. A read is a `ReadState` over `Binding` and a paged read a `PagedState` over `PagedBinding` (`state/core/binding.dart`, the one request runtime, whose settling rules apps' bindings share); a write is a `MutationState` whose calls run in order per key. Each route's arguments are a record type `<Api><Route>Args` of the client method's own parameters (a paged route's position, size and sort are its pager's, its filters `<Api><Route>Filters`). A read over a collection settles its answer into the collection and reads it back out by key, so a write's answer shows at once and a removed entity leaves; a successful write removes the id a DELETE names or holds its answer, then reloads every live read it invalidates (the same `reloaded_reads` answer). `lib/state/<api>_forms.dart` gives each form a `FormShape` (every field path with its `FieldRules`), `create<Api><Route>Form()`, `<api><Route>Body(form)`, `apply<Api><Route>Problem(form, problem)` and, for an update answering its entity, `fill<Api><Route>Form(form, answer)`, over `FormValue` (`state/core/forms.dart`), which app forms' `DtxFormModel` extends; app form fields check the same `member_rules` (`FieldRules` with `min`/`max`/`pattern`; an out-of-range or mismatching value shows `framework.invalid`). `lib/testing/samples.dart` holds `sample<Type>({...})` (every member a named parameter; a member the rule cannot meet a `required` one) and `samplePage(items, maxLimit: ...)`. Flutter apps keep their own `Binding`/`PagedBinding` per owner (each instance its own request, as Angular's per-instance keys), so app behaviour is the same on both targets.
- **Client sync scripts:** every client target declares `PluginDescriptor.client_sync` (`ClientSyncDeclaration`: synced folders and root files, its consumer-file options, and a standard-library-only consumer-check module exposing `library_names` and `check_consumer`); discovery refuses a target without one. For each target generated library-only (`config_resolution.library_only_client_targets`) or published beside apps (`published_client_targets`: the system `clients { <target> { publish = true; } }` block, an app naming the target; the script then also knows the app-only paths the consumer's copy leaves behind, `ClientSyncDeclaration.app_paths`, and a library-form file copied under another name, `library_files`), datrix-codegen-component emits `scripts/sync-<target>-client.py` from one template, inlining the shared sync runtime and the target's check, fronted by the kernel's shared Python-script wrappers without a venv. It verifies the tree's `MANIFEST.json`, refuses before any write when the consumer (Angular: tsconfig `compilerOptions.paths`; Flutter: a `pubspec.yaml` path dependency) maps not every library, refuses to overwrite a hand edit recorded in `datrix-<target>-manifest.json`, then deletes the recorded files and copies; `--check` writes nothing and exits 1 on a difference. Writes stay inside the destination.
- **App-scope constants are literals, emitted as literals:** `const NAME = <literal>;` is a member of `app`, `layout`, `page` and `component`, and a module constant is read in an app by `from <module> import NAME;` (file-level or in the body). The model holds them on each container (`constants`; `datrix_model/ui_constants.py` answers "which constants does this app see", imports included), a page or component sees its `extends` chain's, and `UI026` refuses a non-literal value, an imported constant that is not a literal, and a name shared with a state member or `fn`. Every client target renders a read as the literal itself and declares no member (`datrix_codegen_common.transpiler.client_constants`: `constant_literal_of`, and `inlined_constant_value` where an owner scope is attached), so the emitted tree is the same in every profile; a service's constants stay named declarations.
- **Adding a frontend target is one new package**; no frontend-target name in shared code; no frontend target depends on a backend language package (a TypeScript frontend depends on `datrix-codegen-typescript-core`).
- **Complete apps (D48):** a top-level `app` container, same grammar and statement language as services; backend and frontend containers never share a file; every UI endpoint reference resolves to a real client route; a block of UI code behaves identically on every client target (behaviour-parity gate covers every transpiler-profile package); a surface a target does not realize fails before any file is written; UI-only capabilities never reach a backend body and vice versa; emitted web security headers are one declared set per platform; a custom domain is realized with a certificate or rejected, never ignored. Shell diagnostics `UI037`–`UI040`.
- **Which UI diagnostics read the run's targets:** a `UI0xx` rule whose only input is the source and its `.dcfg` is analysis (`UiValidator`), reported identically by the editor and the CLI. A rule that reads a client target's or the platform's capability declaration is the CLI `check_targets` stage's (`datrix_cli.pipeline.stages.target_checks`; [pipeline-stages](./pipeline-stages.md)), checked against the targets the run actually renders and deploys to, at generation and by `datrix validate --language`: UI002's installed-target row, UI017's native-client row, UI025's realized-set rows, UI032 (strings completeness, whose label keys depend on what each target renders), UI033's native assets, UI034's platform and native-target rules, UI036, UI044's runtime-config row, UI045, UI056's unknown setting and UI057. A client target is web by its declared `web_build` and native by its declared `native_redirect`, never by its name.
- **Asynchronous `fn`s and bindings read recorded facts:** a client target decides which page, component and app `fn`s are `async` with `callable_is_async` (`datrix_codegen_common.transpiler.async_realization`) over the reach analysis recorded and its own declared `AsyncRealization` (`LanguageProfile.async_realization`), never with a call-graph fixpoint or a name match of its own. Dart (`datrix_codegen_flutter.profile.DART_PROFILE`) and Angular (`datrix_codegen_angular.transpiler.profile.ANGULAR_LANGUAGE_PROFILE`, replacing the NestJS backend realization `TS_PROFILE` carries) declare the same client realization: a call of a service's endpoint (`CROSS_SERVICE_CALL`) and every builtin whose row awaits (a `<binding>.refresh()` is the builtin `Binding.refresh`, an awaiting row on both) await, inside lambdas too, and a call of a synchronous `fn` is not awaited (an asynchronous callee's effects already reach its caller). Whether a loop or `catch` variable is bound comes from the read marks analysis records (`datrix_common.datrix_model.reads`: `is_read`, and `is_read_beyond_rethrow` for a clause whose exception is only rethrown, which Dart renders `on T { rethrow; }` with no binding). A form's lifecycle code is a client-declaration body, which owns no callable facts. Every view-element argument and modifier, style and theme value, page `meta`, nav link modifier and form, table or workspace member is resolved too, by its slot in `datrix_common.datrix_model.ui_vocabulary` (see [pipeline-stages](./pipeline-stages.md)): a name of code carries the declaration it reads or calls, and a word of the UI vocabulary carries the page, asset, style, theme token or vocabulary term it names. The one builtin-use census (`datrix_common.datrix_model._ui_shared.iter_target_builtin_uses`, read by UI025, the web Permissions-Policy, the native usage descriptions and the builtin-realization stage) keeps a use only when its root was recorded as a builtin object (`BuiltinCategory`), and the UI rules that classify a name -- UI013's bound member, UI020's navigation calls, UI021's no-client-home receivers, UI027/UI028's called `fn` -- read the recorded target too: a state member, local, parameter or `fn` spelled `Nav` or `Biometric` is never the builtin and selects no permission.
- **List wire contract:** each `ClientRoute` carries its `read_shape` (`PAGED`, `LIST`, `SINGLE`, `MUTATION`) and its `list_query` rows (`derive_list_query_rows`); a client method takes the declared parameters, a paged route's optional pagination pair, the rows' derived filters (typed as their fields) and, on a sortable route, `sortBy?: <Api><Route>SortField` and `sortOrder?: 'asc' | 'desc'`, every one sent through `toHttpParams` under the contract's wire key. The Angular client exports the `<Api><Route>SortField` union of the route's sort values beside the client class (the API name keeps two APIs' same-named routes apart in their service's one library index); the Flutter client takes the same arguments. A client may request a page size: the server bounds it (an out-of-range size is a `request-validation` problem, never clamped) and reports the size it applied (`limit`) and the largest it accepts (`maxLimit`).
- **Paginated routes (`Page<T>`):** a route returning `Page<T>` answers the envelope `{items, total, offset, limit, maxLimit}`; the Angular client types it `Observable<Page<T>>` (`core/page.ts` in the shared `<system>-api-common` library) and the Flutter client `Future<Page<T>>` (`lib/api/core/page.dart`). The paged binding (Angular: the facade's paged handle under a `PageView`; Flutter: `PagedBinding` in `state/core/binding.dart`) loads **one page per request** — no lookahead — and exposes `rows`, `total`, `offset`, `limit`, `maxLimit`, `pageCount`, `pageIndex`, `hasNext`, `hasPrevious`, `range`, `window`, `next()`, `previous()` and `goTo(index)`; it owns the position, the requested size, the sort and the filters (each change returns to the first page), so a UI call to a paginated route passes no `PageRequest` (`UI042`), and a later page answering with a different size restarts from the first page. The pager (table footer and paginated `list`) shows the range caption ("Showing 26–50 of 340"), previous, a numbered window and next. The window is **one algorithm**, `datrix_codegen_common.generation.ui_pager` (`PAGER_BOUNDARY_COUNT`, `PAGER_SIBLING_COUNT`, `pager_window`), rendered into both runtimes as `pageWindow` (Angular: once, in `<system>-api-state-common`'s `pager.ts`) and tested against the same case table (`PAGER_WINDOW_CASES`) emitted into each target's generated tests. Framework strings `framework.showingRangeOfTotal`, `framework.pagination`, `framework.pageNumber`, `framework.pageSize`.
- **Form members fixed by code:** `field x : fixed(expr)` is a body member a form sends without showing (`UiForm.fixed_fields`, built once in `datrix_codegen_common.generation._ui_contract_fields`; `datrix_common.datrix_model._ui_table_derivation.fixed_form_members` is the one selection rule, so no step or `fields(auto)` shows it). Every client target reads the expression when the form submits and shows a server error on it at the form's level; a `label(Msg.<key>)` makes it one review row. A required member whose expression is unset at submit is never sent: the form shows one form-level error per submission naming each such member by its label (its derived field label without one) followed by `framework.required`, and `UiFixedField.must_be_set` (the body requires the member) is the one fact every target reads. Rules `UI058` (`datrix_semantic.validators.ui_fixed_members`).
- **Money inputs:** `field x : money(currency: <expr>)` and `number(...) : money(currency: <expr>)` edit a whole number of a currency's minor units as the major-unit amount (`UiFormField.money_currency`, built in `datrix_codegen_common.generation._ui_contract_fields`; the currency table is the one `Fmt.minorMoney` reads). Every client target keeps the value as the integer, reads and writes the text on the integer's digits in the session locale, treats text that is no amount as invalid (never rounded or skipped), and shows a review row through `Fmt.minorMoney`. The currency is a code (checked against ISO 4217 at generation), a state read, or `draft.<field>` by itself (another field of the form; any other read of `draft` is refused). Rules `UI059` (`datrix_semantic.validators.ui_money_inputs`).
- **Element state modifiers:** `disabled(<Boolean>)`, `placeholder(Msg.<key>)` and `hint(<text>)` are one vocabulary entry each (`DISABLED_*`, `PLACEHOLDER_*`, `HINT_*` in `datrix_common.datrix_model.ui_element_shapes`; slots in `ui_vocabulary`), checked once in `datrix_semantic.validators.ui_view_elements` (`UI015`, `UI022`, `UI031`) and, for a form `field`, in `ui_form_placeholders` (`UI016`; a form's placeholder reaches a target as `UiFormField.placeholder_key`, so both targets read one derivation). Every client target realizes each on every element that takes it: `disabled` keeps the control present, announced unavailable and inert while the condition holds, and a `null` condition leaves it available (Angular: the `disabled` property, and on an anchor `aria-disabled` with its `routerLink`/`href` answering `null`; Flutter: the widget's `enabled:`); `placeholder` is the text-entry hint text (Angular `placeholder` attribute, Flutter `InputDecoration.hintText`), never the label; `hint` is the element's accessible description and a tooltip on hover and keyboard focus, drawn as text only, with `null` or empty text drawing none (Angular: ui-core's `UiHint` directive over `aria-describedby`; Flutter: `DtxHint` over `Tooltip`, and an `iconButton`'s hint joins its own tooltip). An element that carries none of the three is emitted exactly as before; the shared runtime libraries gain only the directive/widget and parameters. Two more states follow the same shape (`BUSY_*`, `CHECKED_*`, `CHECKED_MULTIPLE_*`; `UI022` `busy_type` / `checked_type`, `UI015` `multiple_without_checked`): `busy(<Boolean>)` on a `button` / `iconButton` shows a progress indicator in the leading position and drops every activation while keeping the control enabled and focusable (Angular: `aria-busy` + `data-busy` over a click handler gated on the condition, the ring a ui-core rule that turns only under `prefers-reduced-motion: no-preference`; Flutter: `busy:` on `DtxButton` / `DtxIconButton`, a `CircularProgressIndicator` drawn still when the platform disables animations), and `checked(<Boolean>)` (+ the `multiple` flag) on a `menuItem` is a radio or checkbox menu item with a check mark (Angular: `role="menuitemradio"` / `menuitemcheckbox` + `aria-checked`; Flutter: `DtxMenuItem(checked:, multiple:)` over `Semantics(checked:, inMutuallyExclusiveGroup:)`). `lines` (`STYLE_LINES_PROPERTY`, `UI018` `lines_count`) is a style property compiled by `ui_stylesheet` (Angular: single-line clip or a line clamp) and by Flutter's `DtxStyle.lines`; a table column's `style(...)` reaches the cell as `UiColumn.style_key` (Angular: a span with the style class; Flutter: `DtxStyledCell`). `preserveLines` (`text`) and the `code` element keep a value verbatim (`white-space: pre-wrap` / `pre` + `overflow-x: auto`; Flutter `DtxText(preserveLines:)` — a `text` without it collapses white space on both targets — and `DtxCode`). Held across targets by the `client_element_state` probe (`RealizedElementState.busy` / `.checked`).
- **Enum tones in table cells:** a cell over an enum-typed column that no `render(...)`/`format(...)` presents shows the member's label (`UiColumn.shows_enum_label`), and when a member of the enum declares a `tone(...)` every client target draws it as its `badge` in that member's tone (`UiColumn.member_tones`, the one rule; an absent optional value draws nothing, an enum declaring no tone stays plain text). `UI018` checks those tones against the theme as it checks a view's (`enums_drawn_by_columns`, `datrix_common.datrix_model._ui_table_derivation`).
- **Choice lists:** `field x : options(route, value: r => r.key, label: r => r.text)` and `select(...) : bind(m), options(route, value:, label:)` choose among the rows of a `get` route (`UiFormField.choices` / `UiElement.choices`, a `UiChoiceSource` built in `datrix_codegen_common.generation._ui_contract_fields` and `_ui_contract_view_tree`; the accessors are wire property paths). A form field loads its rows when the form opens (the form is not shown before), a `select` element reads them through a synthetic data binding the owner declares, so the region around it waits. Every client target stores the key of the row picked (its own type) and shows the row's text, in the review step too. A page rendering the form reaches the route as it reaches `submit` (`form_choice_calls`). A `Page<T>` route is read a page at a time (`UiChoiceSource.paged`): a form field through a paged view or binding of its own (the form does not wait for it), a `select` through its synthetic binding, which is then paged; `search: q` (`UiChoiceSource.search` / `UiBinding.search`, a `ListFilterRow` of the route's declared text filters) sends the typed text as that filter. Every target draws the one picker rule of `datrix_codegen_common.generation.ui_choice_picker` (an `Array<T>` list of at most `CHOICE_COMBOBOX_THRESHOLD` rows is a menu, a longer or paged one a searched picker; search sent after `LIVE_INPUT_DELAY_MS` of `ui_live_input`, the one pause a table's `live` filter and a `debounce(...)` input wait too; the row picked kept), held to its `COMBOBOX_CASES` / `MATCH_CASES` tables in each target's generated tests: Angular's `<ui-choice-picker>` (`ui-core/elements/choice-picker.ts`), Flutter's `DtxChoicePicker` (`core/inputs.dart`). A choice of several keys is the same `options` on a form field holding an `Array` of keys or on a `multiSelect` bound to one (`UiChoiceSource.multiple`; a field of natural kind `repeatableInput` becomes `multiSelect` with review kind `choices`), with an optional last `group: r => r.heading` (`UiChoiceSource.group_path`) and, on a `multiSelect` only, an `Array` in scope in place of the route (`options(summary.years)`, `UiChoiceSource.items`; `UiChoiceSource.rows` is the one accessor for either, and no synthetic binding is made for it). The picker writes the whole array, keeps the keys of rows on no page shown, and the review lists the labels; it is the same picker as the single choice, a checkbox group at or below `CHOICE_COMBOBOX_THRESHOLD` rows read whole and otherwise the searched picker with chips (`uses_checkbox_group`), held to `TOGGLE_CASES` / `GROUP_CASES` (`toggled_keys`, `grouped_rows`) in each target's generated tests: Angular's `multiple` input of `<ui-choice-picker>` (a form field binds it through `__setKeys`, since an `Array` member is a `FormArray`), Flutter's `DtxMultiChoicePicker` / `DtxMultiChoiceListField`. The language declares no collection length bound, so the picker validates none. `description: r => r.text` (`OPTIONS_DESCRIPTION_ARGUMENT`, between `label:` and `search:`; `UiChoiceSource.description_path`) shows a sentence under each choice and is the control's accessible description; a plain select / menu cannot show it, so a single choice over described rows is the searched picker (`uses_combobox(rows, paged, described, multiple)`, held to the extended `COMBOBOX_CASES`). The `cards` flag (`CARDS_MODIFIER`, `UiChoiceSource.cards`, refused over `search:` or a paged route: `UI060.cards_search` / `cards_paged` / `cards_without_options`) draws a list read whole as one selectable card per choice in a grid under the `group:` headings (`shows_cards`, held to `CARDS_CASES`): Angular's picker draws labels around native checkboxes / radios, Flutter's `_DtxChoiceCards` draws `Semantics`-wrapped cards with a mark and a heavier border. Rules `UI060` (`datrix_semantic.validators.ui_choice_sources`; `multi_type`, `group_single`, `list_*` for a list in scope).
- **Colours:** `color(label?) : bind(member)` (`INPUT_ELEMENTS`) and `swatch(value, label)` (`CONTENT_ELEMENTS`, roles `(VALUE, TEXT)`) are the two `COLOR_ELEMENTS` of `ui_element_shapes`; a form field of the `Color` scalar derives input kind `color` (`COLOR_INPUT_KIND`, `derived_input_kind`; `UI013` restates it in `_ui_checks_views`, where `input` stays an alternate for a `Color` member). One rule, `datrix_codegen_common.generation.ui_color_value`: `#` and six hex digits, the `Color` scalar's own grammar (`DOMAIN_FORMATS["Color"]`) rendered once as `COLOR_REGEXP_SOURCE`, a colour written in lower case (`canonical_color`), held to `COLOR_CASES` in each target's generated tests. No alpha channel. Web targets draw both with ui-core components, never a native tag (`web_client.elements` excludes `COLOR_ELEMENTS`): `<ui-color-input>` (a `ControlValueAccessor` and `Validator`: the platform picker beside the hex text, writing a colour only once it is one) and `<ui-swatch>` (an SVG `circle` whose `fill` is an attribute set from the canonical colour, so no `style` attribute or `unsafe-inline` is involved). Flutter: `DtxColorInput` and `DtxSwatch` in `core/inputs.dart`, a `DtxFieldKind.color` text field for the form field (`DtxColorPickButton` opens the channel-slider dialog).
- **Toast tone:** `Ui.toast(message, tone: <tone>)` (`ui_tone_arguments` in `datrix-common`; `tone` names a theme tone, `UI018.call_tone` / `call_tone_not_a_word`) shows the message in that tone, `info` when it names none. One rule for every client target, `datrix_codegen_common.generation.ui_toast` (`toast_is_alert`, `toast_display_ms`, held to `TOAST_CASES` in each target's generated tests): a `danger` toast is announced as an alert and stays longer, every other tone as a status. - **Page sizes and sortable headers:** one rule each, `datrix_codegen_common.generation.ui_pager_controls`, rendered into every client runtime and tested against `PAGE_SIZE_CASES` and `SORT_CYCLE_CASES` (Angular `pager-controls.spec.ts`, Flutter `test/core/pager_controls_test.dart`). The flag `firstLastPager` (`Table.first_last_pager`, the element modifier; `FIRST_LAST_PAGER_MODIFIER`) puts a first-page and a last-page control (`framework.firstPage` / `framework.lastPage`) around the previous/next pair, each disabled on the page it goes to (`first_last_controls`, held to `FIRST_LAST_CASES`: Angular `pager-ends.spec.ts`, Flutter `pager_controls_test.dart`); a binding has one pager, so `binding_first_last_pagers` unions the lists over it and `UI054` (`first_last_conflict`, `first_last_not_paginated`) refuses a disagreement or a non-paginated source. A sortable header is a button cycling none → ascending → descending (`next_sort`) from the first page and carries its sort state (`aria_sort`: Angular `aria-sort`, Flutter `DataTable.sortColumnIndex`/`sortAscending`). A table's filters are its route's list-query filters, declared and derived (`route.list_query.filters`). A body-level call to a paginated route (from an `fn`, an event slot, a state initializer or a test body) is refused at analysis (`UI053`) on every client target, since a body owns no page position and has no envelope to read; bind the route with `data { }` instead. A test's `respond`/`respondError`/`called` names the binding's own call and is checked as that binding (`UI042`).
- **Selected rows:** `selected(condition)` on a `table` declaration (`Table.selected`, `InheritedTable.selected` the nearest declared, `UiTable.selected`; `TABLE_SELECTED_MODIFIER`) is a view expression over the table's `row` (`TABLE_ROW_BINDING`, bound the way a `rowAction`'s handler binds it, `ui_vocabulary._table_roots`) and the app's state; it is presentation only, and `UI022.selected_type` refuses a value that is never a Boolean (`_ui_boolean_condition.is_not_boolean`, shared with `disabled(...)` and `poll(until:)`). Angular draws the row's `tr` with `aria-current="true"` and `data-selected="true"` when the condition holds (a `table` role has no selection semantics; `aria-selected` is a grid's) and styles `[data-selected]` in the primary tint, bold; Flutter passes the predicate to `DtxTable.selected`, which sets `DataRow.selected` and announces the first cell selected. A table declaring none emits no selection binding on either target.
- **Disclosures:** `section(title) : collapsible[, open]` (`DISCLOSURE_ELEMENTS`, `DISCLOSURE_OPEN_MODIFIER`; `collapsible` is the sidebar's flag word too, so `ELEMENT_MODIFIER_KINDS[SIDEBAR_COLLAPSIBLE_MODIFIER]` is the sidebar plus `section`) is a titled container the reader shows and hides. State is the platform widget's own, so every rendering (a `foreach` or item-template instance included) toggles independently and no state member is generated: Angular emits a native `<details data-kind="section">` whose `<summary data-part="header">` holds the title (`ElementTemplateNode.disclosure_open`; header actions lead the body), Flutter a `DtxDisclosure` (an `ExpansionTile`, `initiallyExpanded: open`). `UI063` refuses an untitled disclosure, one that is also a link, and `open` without `collapsible`; `UI038` still refuses `collapsible` on any other element. Held by Flutter `test/core/disclosure_test.dart`.
- **Row styles:** `rowStyle <style> : when(<condition>)` is a table member (`TABLE_ROW_STYLE_KEY`, `ROW_STYLE_WHEN_MODIFIER`; the condition is bound over `row` through `MEMBER_MODIFIER_BOUND_NAMES`, so members merge down the `extends` chain by style name), read by `datrix_common.datrix_model.ui_row_styles` (`row_style_rules`, `ROW_STATE_STYLES`, `row_style_opacities`, `row_style_text_color`). The style is an app style or a fixed state (`muted`); the contract's `UiTable.row_styles` carries each rule and `_build_styles` adds a `UiStyle` for a fixed state the app does not declare, so both targets draw it through their existing style mechanism: Angular binds `[class.style-<name>]` to the condition on the row's `tr`, Flutter passes `DtxRowStyle`s to `DtxTable`, which wraps each cell in `dtxStyled`. `UI062` (shape, unknown style, duplicate), `UI022.row_style_type` (Boolean) and `UI018.row_style_contrast` (the dimmed text colour keeps 4.5:1 over the theme's surface in every scheme) check it before generation. Held by Flutter `test/core/table_row_style_test.dart`.
- **Form edit state:** `form(X) : ref(editor)` on a page or component (`FORM_REF_MODIFIER`, `UiSlot.FORM_REF`; `datrix_model.ui_form_refs.form_refs_of` is the one derivation, `InheritedMembers.form_refs`) defines `editor` beside the owner's `state`, `fn`s and `data` bindings; `editor.dirty` (Boolean) and `editor.reset()` are the `FormHandle` builtins (`BuiltinGroup.FORM`, client axis; every client target maps both rows). The contract carries `UiPage.form_refs`/`UiComponent.form_refs` (`UiFormRef(name, form, shown)`: an element its own `targets(...)` scopes away from a target keeps the name, `shown` is false there, so the handle is never dirty) and `UiApp.handled_forms`, the only forms a target gives the extra members to (a form shown without `ref` generates byte-identically). One comparison rule, `ui_form_edit.form_values_equal`, over the wire values of the shown members (unset equals missing, ordered lists, member-wise groups, a text never equals a number), rendered into every target's runtime tests as `FORM_VALUE_CASES`; a form opens with the values it holds after load and `onLoad`, a successful submit re-baselines, a fixed member is never part of it, and `reset()` restores the opened values and clears the form's messages. `UI015.form_ref_name`, `UI028.form_ref_duplicate`/`form_ref_shadowing`/`form_ref_layout` refuse a handle that is not a bare name, is named twice or like another member of the owner, or sits in a layout. Angular: `ui-core/elements/form-handle.ts` (`FormHandle`, a getter over the form's signals), the form class takes the `formHandle` input; Flutter: `DtxFormHandle` and `DtxFormModel.markOpened/dirty/restoreOpened` in `core/forms.dart`, the form widget takes `formHandle`.
- **Live inputs:** one pause for every input that acts on typed text, `ui_live_input.LIVE_INPUT_DELAY_MS` (300 ms; `live_input_template_globals()` hands it to each target's templates, and the choice picker's search delay is the same value). A table `filter x : live;` (`TABLE_FILTER_LIVE_MODIFIER`, `DeclaredFilter.live`, `UiFilter.live`; text controls only, `UI022.live_filter_type`) applies the filters after that pause as well as on Enter, returning to the first page like Search. `debounce(300ms)` on `input`/`textArea`/`search` with `bind(...)` (`DEBOUNCE_MODIFIER`; `ui_debounce`, the one reader of the duration, 1 to 10 000 ms, `UI015.debounce_*`) holds the write into the state member back by its own pause, Enter writes at once and the newest text wins. A `ms` literal is a `duration_ms` `LiteralNode` (every other duration keeps its seconds), so `poll(300ms)` still refuses. Angular: `Debouncer`/`UiDebounce` in `ui-core/elements/live-input.ts`, the table class holds one `Debouncer`; Flutter: `DtxTextInput.debounce`, `DtxFilterField.live` with `dtxLiveInputDelay`.
- **Failed requests of a data binding:** one rule for every client target, stated in `datrix_codegen_common.generation.ui_binding_outcomes` and tested against its case table (`BINDING_OUTCOME_CASES`) emitted into each target's generated tests (Angular `binding-outcomes.spec.ts` over the state runtime's request state, Flutter `test/core/binding_test.dart`). The answer shown stays while a newer request loads. A failed refresh (`refresh()`, a `poll(...)` tick, a retry) of a value loaded for the same inputs keeps the value: the binding stays loaded and its `error` holds the failure, and the gate's loaded branch shows a stale notice (`framework.refreshFailed`, the problem's title, a retry) above the data. A failed load (the first, or one for changed inputs) drops the value and shows the error state in place of the content. Gates split the two: `firstFailedLoad` replaces content, `firstFailedRefresh` feeds the notice.
- **When a polled binding stops polling:** one rule for every client target, stated in `datrix_codegen_common.generation.ui_poll_outcomes` and tested against its case table (`POLL_OUTCOME_CASES`) emitted into each target's generated tests (Angular `views.spec.ts` over the state runtime's views, Flutter `test/core/binding_test.dart`). `poll(Ns, until: <condition>, max: N)` lowers to a stop predicate over the loaded value (Angular `stopWhen: (job) => …`, Flutter `stopWhen: (job) => …`: the binding's name is the closure's parameter, never a read of the binding itself) and a tick cap (`maxPolls`). A tick does not refresh once the value shown satisfies the predicate; after the cap the binding reports `pollExhausted` until `resumePolling()`; a load for changed inputs (arguments, filters, page, size or sort) polls afresh from zero. `UI019` refuses a cap below 1 and a condition that never reads its binding or is not a Boolean.
- **Per-rendering view state:** state a user sees per rendering of an element lives on that rendering, never on one owner member a loop would share: a `menu` panel's id and open state on `dtxPopover`, a `tabs` container's id prefix and unbound selection on `dtxTabs` (Angular; Flutter widgets keep their own state). A bound `tabs` reads and writes the one state member it names, so every rendering shares that selection on every target.
- **Static sites (`rendering('static')`):** an app prerenders to one HTML document per page and locale (diagnostics `UI043`–`UI048`, `UI052`; `datrix_semantic.validators.ui_static_checks`). A static app reaches nothing beyond its documents — no `uses`, `login`, `push` or runtime-config block (`runtime_config_blocks`, hoisted to `datrix_common.datrix_model.ui_runtime_config` so analysis and generation read one answer) — and every target it lists must build a web bundle. Locales are path prefixes (the default locale unprefixed); the route's locale is the session locale. Angular realizes it with `@angular/ssr` server routes (`app.routes.server.ts`: every routed path × locale, one document per key of a `from(...)` collection, redirects as meta-refresh, `404`), a server entry (`main.server.ts`), browser-side hydration without event replay (no inline script), a `SiteMetaStrategy` setting each head (description, canonical, `hreflang` alternates, Open Graph, robots), and persisted state restored after the first render. Angular's Router constructs the app's `TitleStrategy` while the Router is itself under construction, so nothing the strategy constructs (its messages, the session behind them) may resolve the Router then — doing so is a dependency cycle (NG0200) and a blank app: the session resolves the Router on use, a static app's `provideRouteLocale()` app initializer makes the session follow each navigation's locale, and `SiteMetaStrategy` reads the route from the snapshot the Router passes to `updateTitle`. `datrix-codegen-angular`'s `tests/integration/test_title_strategy_construction.py` and `test_static_rendering_emission.py` walk the emitted construction-time injections from each app's strategy and fail if the Router is reached. `scripts/build-app.mjs` is the one build entry every platform runs: it runs `ng build`, then for a static app requires and validates the build inputs, replaces the origin and robots placeholders, renames `404/index.html`, writes `robots.txt` and (when indexable) `sitemap.xml`, and fails on any inline executable script. `site-manifest.json` carries the profile-independent page list.
- **Build inputs and routing plan:** the origin and indexability of a prerendered site are build environment, never generated source (`datrix_codegen_kernel.generation.site_build_inputs`: `DATRIX_SITE_ORIGIN`, `DATRIX_SITE_INDEXABLE`; `AppWebConfig.indexable` defaults to `false`). Every platform that builds a static app passes exactly those keys and proves it (`require_site_build_inputs_supplied`). One `WebRoutePlan` (`datrix_codegen_kernel.platform.web_route_plan`) answers which paths exist, what an unknown path answers, which paths redirect and how files are cached and typed, and each platform renders it: nginx (`try_files`, `error_page 404 /404.html`, exact-location `301`s), a CloudFront viewer-request function plus 403/404 error responses, and Static Web Apps `routes`/`responseOverrides`. `WEB_CONTENT_TYPES` covers every extension a bundle can contain (including `avif` and `webp`), proven by `require_content_types_cover`. The plan's `paths` are the one set every platform serves: a static app's are its routed pages (`ui_derivation.routed_paths`, workspace sections included); a client app's add every path its router answers -- each redirect source and the hosted-login routes (`datrix_common.identity.hosted_login_paths.BROWSER_HOSTED_LOGIN_PATHS`: login, login callback, logout callback, forbidden), so the identity provider's redirect back to the app is answered `200`. No platform re-derives the set (Azure's `staticwebapp.config.json` rewrites, the CloudFront router function and nginx all read `plan.paths`). The hosted-login paths have one home: each client target renders its router/guard/session constants from it (`datrix_codegen_common.generation.ui_hosted_login.hosted_login_template_globals`), and every identity-provider registration derives a browser client's redirect and logout URIs through `browser_redirect_uri`/`browser_logout_uri`; `datrix-codegen-angular`'s `test_hosted_login_routes_served.py` compares the emitted route table with the plan in both directions.
- **Content, images, reveal (every app, every target):** `content` collections are authored as files (TOML front matter + Markdown), read once at generation time by `datrix_common.datrix_model.ui_content` and compiled in (`UI049`, `UI050`); `from(Collection)` pages enumerate their documents. Declared `image` assets and content image fields are encoded once by `datrix_codegen_kernel.assets.image_variants` (AVIF/WebP plus the source format, content-addressed, every raster re-encoded without metadata, byte-identical for a fixed input; a Pillow lacking one of those encoders -- its Windows ARM64 and iOS wheels carry no AVIF -- is refused by `require_image_encoders` before any encoding, never a dropped format) and drawn by `ui-image` (Angular, `<picture>`) or `ResponsiveImage` (Flutter, WebP renditions); `image(asset, Msg.alt)` carries alt text and `: eager` marks the first image. `: reveal` is a flag realized by `UiReveal` (Angular) and `Reveal` (Flutter), skipped under reduced motion (`UI051`). Angular's ui-core reads browser globals only through `BrowserPlatform` (a census test holds this) and sanitizes Markdown through a `MARKDOWN_SANITIZER` token, so one ui-core serves the browser and the prerender.
- **External links:** `externalLink(label, url)` / `externalLink(label) : configured(name)` is the one element that opens an address outside the app (`EXTERNAL_LINK_ELEMENT`, role `URL`, in `ui_element_shapes`). What may be opened is one rule, `datrix_common.utils.network.external_url_refusal` / `EXTERNAL_URL_SCHEMES` (absolute `https`/`http`, a host, no credentials): UI015 applies it to a literal, the `AppProfileConfig` validator to each `externalLinks { }` entry, the producer (`datrix_codegen_component.client_runtime_generator`) before it writes the entry, and each client's generated `externalUrl` / `externalUrl()` to a computed address and to every loaded entry (the schemes are rendered from the constant, never retyped). A computed address that fails the check opens nothing (Angular: no `href`; Flutter: `openExternalLink` returns). `configured(name)` reads the profile's entry through the `externalLinks` runtime-config block, which `runtime_config_blocks` requires iff `app_configured_link_names(app)` is non-empty (UI034 holds every name declared; UI044 refuses it on a static-rendering app). Angular binds `[attr.href]` on `<a target="_blank" rel="noopener noreferrer">` through `NavService.external` / `.configured`; Flutter presses a `DtxLink` into `openExternalLink` (`url_launcher`, external application mode).
- **Write-only secrets:** a text member of a request struct declared `: writeOnly` (`FIELD_MODIFIER_WRITE_ONLY`; `field_is_write_only`) is withheld from every response by the one withholding rule (`field_excluded_from_response`) and is the one withheld field a form derives, as input kind `secret` (`SECRET_INPUT_KIND`), never prefilled and never in `UiForm.review_fields`. `input(...) : bind(m), masked` (`MASKED_MODIFIER`) is the same input in a view. `ENT015` refuses it on an entity/trait/view, on a non-text member and on a struct an endpoint returns; `UI013` a masked input over a non-text member or with `debounce`; `UI035` one bound to persisted state; `UI012` still refuses a table column naming it. Angular renders `<ui-secret-input>` (a `ControlValueAccessor` plus `model`), Flutter `DtxFieldKind.secret` / `DtxTextKind.secret`; the reveal control's names are the `framework.showSecret` / `framework.hideSecret` strings every non-default locale restates (`UI032`).
- **Runtime-column tables:** `dataTable(columns: x.columns, rows: x.rows, cells: row => row.cells)` (`DATA_TABLE_ELEMENT` in `ui_element_shapes`) shows a header of texts and rows whose cells an accessor reads. A client contract carries one list level (`_client_contract_type_closure` refuses a list inside a list), so a row is a struct whose member holds its cells; the shape's `rows_argument` stands in for `data:` (`DataElementShape.items_argument`), types the `cells:` accessor (result `texts`, an `Array<String>`) and keys the derived empty state (`empty_state_argument`).
