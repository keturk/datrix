# Pack: RDBMS Schema Convergence Contract

**Read when:** you touch schema snapshots, the schema converge, `schemaConvergence { }` config, or the kernel's schema rendering.
**Not for:** startup readiness of the generated service ([runtime-and-deploy.md](./runtime-and-deploy.md)).
**Core map:** [architecture-cheat-sheet.md](../architecture-cheat-sheet.md)

Language-neutral, UUID-scoped. Every deploy converges each block's live catalog `L` to its declared schema `D`: `schema.json`, the canonical snapshot generation writes into the block's schema tool. No migration history, revision chain, recorded baseline or generator state is kept: both sides of every comparison are produced fresh on each deploy, `D` by generation and `L` by the engine's catalog reader.

- Every `RdbmsConfig` requires `id: UUID` in its `.dcfg`. A destructive change runs only with the deploy's `--approved` switch, and some changes are never applied (`datrix-rdbms-schema/docs/architecture.md` § Convergence outcomes).
- **One converge per deploy.** `deploy`'s `converge` step (`converge_schema_blocks`, `datrix-codegen-kernel/docs/architecture.md` § Converge) reads every block, plans it (`schema.py plan`, `--approved` exactly when the deploy was given it) and prints the plan; a plan refusing a change stops the deploy, naming every refused block, before anything applies. Then each block's expand SQL is applied, each block is re-planned and the re-plan must hold exactly the first plan's contract changes, the new release starts and is verified healthy, the contract SQL is applied, and each block is read again and `schema.py verify` compares it with `D`; a block that differs fails the deploy. Each change has one outcome (`convergence_outcome`): applied safe, applied risky (validated over the rows, an offending row fails the apply naming the constraint), needs approval (in the contract phase, and only with `--approved`), or never applied. `deploy --plan` plans every block and changes nothing; `deploy --plan --approved` prints exactly what an approved deploy would run, removals included.
- **An object the database holds and `D` does not declare is removed only with approval.** `undeclared_object_changes(L, D)` names every table, column, index, unique constraint, foreign key, enum type, check and trigger `L` holds that `D` does not state; `removal_outcomes` refuses each removal without `--approved`, naming the object and the switch, and an approved deploy drops it with its data. A check whose name is definition-derived (a check `D`'s rules produced and `D` no longer states) and a Datrix trigger whose declaration was removed are dropped without approval. Narrowing a column back to a shorter type needs approval too.
- **A rollback is a deploy of the earlier output.** There is no rollback path: deploying an earlier release converges the database to that release's `D` like any other deploy. What the later release added and the earlier `D` does not declare -- its tables, columns, indexes, unique constraints and foreign keys, with their data -- is removed, and a column the later release widened is narrowed back, only when the deploy is run with `--approved`; without it the rollback is refused, naming each object. The checks the later release derived from its rules are dropped without approval. Deploying the later output again converges forward, recreating what was removed, empty. A live test converges a database to a later release, back to the earlier one and forward again on every registered engine (`datrix-codegen-sql/tests/integration/test_rollback_live.py`).
- **The SQL is rendered once per dialect, by the kernel.** No language plugin declares a migration adapter (`LanguagePlugin` has no such member), and the deploy's schema client applies every schema.
- **One migration path.** The deploy's schema converge builds and changes every block's schema (`converge_schema_blocks`). `datrix generate` renders no migration: `--migrations`, `--allow-destructive`, `--migration-format` and `--carry-forward-live-snapshots` are unknown options, `PipelineConfig` carries no migration fields, the pipeline has no migrations stage and no `datrix migrations` command exists. `datrix_rdbms_schema` renders no migration text of its own (it holds the snapshot, diff, policy and convergence planner), so there is no second type map or DDL emitter to keep in step with the kernel.
- **One schema and one apply lock per `rdbms_id`, converged once by the deploy.** No generated service migrates its database or holds a DDL credential, on any platform or in any language: the deploy's schema client converges every block (`converge_schema_blocks`) and alone reads the block's owner login. A shared block is converged once, under the advisory lock the block's dialect derives from the `rdbms_id` (`SQLDialect.session_lock_sql`, failing closed on a dialect without one). The block's chain applier, the first consumer by qualified name holding `readwrite` (`shared_chain_applier`; a block every consumer reads is SHR014), only names the block's owner. Every consumer, a reader or a writer, connects as a service or reader login of its own, which holds data rights and no DDL right, and none applies a schema. A reader connects with a credential that can only read. Docker gives it a SELECT-only login created by a one-shot reader provision. Azure App Service gives its Entra role CONNECT, USAGE and SELECT plus default SELECT for the applier's role. Azure VM refuses a reader, because every container shares the VM's identity. AWS gives it a SELECT-only login that the stack provisioning the database creates with an in-VPC custom resource realizing the database's access plan, connected as the database's master login (the plan's owner) with full certificate verification; a reader of a shared database AWS does not provision is refused, since no login could be created for it. On every platform a login's password is a secret of its own: the application secret placement stores it as `<login>_password` and resolves the holder's `<block>_password` to it (`PlacedSecret.read_as`), and the master credential is never re-exported, exposed or granted to a reader. The seed of a shared block runs only in a `readwrite` consumer, inside the block's session lock. Whether a service seeds in its own process at startup is one platform fact, `run_seeds_at_startup`, read by every language through the kernel's `service_runs_startup_seeds_in_process`; the seed takes the block's session lock in its dialect (never a hardcoded `pg_` statement), and no platform runs a migration container, task or in-process step. The platform's health windows render their configured values. Who is a consumer is answered once, by `datrix_common.datrix_model.shared_rdbms_scope` (`realized_rdbms_blocks`, `shared_rdbms_consumers`); per-block access emission walks the realized blocks while schema ownership (DDL, `rdbms_id` validation, provisioning) stays with the owner. SHR007 rejects a write through `readonly` access, including in the lifecycle hooks of a consumed entity, which run in each consumer that writes it. SHR008 rejects an alias collision, SHR009 an unconsumed shared block, and SHR014 a shared block no consumer may apply. A consumed entity's hook may call the shared container's functions and read its constants: each writing consumer realizes the ones its hooks reach, transitively, exactly as it realizes an imported module's (`datrix_common.datrix_model.shared_declarations`). A reader emits no lifecycle hooks.
- **One index set per table.** `datrix_rdbms_schema.schema_snapshot.entity_table_indexes` is the table's index set -- each declared index over exactly the columns it lists (a `Tenantable` entity too; the trait's `indexed` `tenantId` gives the tenant index), then field-level `: index` and the spatial index a geographic column implies -- recorded by the snapshot and created by the SQL generator's DDL alike.
- **A column's DEFAULT and `: unique` are converged facts.** The snapshot differ (`compute_snapshot_diff`) emits `FIELD_DEFAULT_CHANGED` / `FIELD_UNIQUE_CHANGED`; the kernel renders them through `datrix_codegen_kernel.sql_facts.snapshot.column_constraint_change` over the kernel dialect (`SET`/`DROP DEFAULT`, a unique constraint added as `uq_<table>_<col>` or dropped by a catalog lookup of the column), the default after every other change (`schema_change_order`). Every table is created with its declared defaults as database defaults, and a column added later ends up as one created with its table. A collection literal default is recorded as the JSON document it declares (`datrix_common.datrix_model.collection_default`), never shortened. Which DDL an engine speaks is one fact, `RdbmsEngine.ddl_dialect`, resolved by `get_sql_dialect` and every dialect-keyed table.
- **A column is identified by its column name, never its DSL field name.** The snapshot differ matches a table's fields across two snapshots by `SnapshotColumn.column_name`, so a field renamed only in its DSL spelling (`heightAGL` → `heightAgl`, both `height_agl`) is no change, while a rename that moves the column is a `FIELD_REMOVED` plus a `FIELD_ADDED`, so an approved deploy drops the old column with its data. `snapshots_describe_the_same_schema` compares columns by the same identity. A change still names its field by DSL name: a removed column by `L`'s name, every other change by `D`'s.
- **One schema authority, one index-naming rule.** `D` is the only description of the schema the converge renders: no generated service asks an ORM to diff entity models against the database at run time. Every index and unique constraint is named by `datrix_rdbms_schema.index_naming` (plain `ix_`, declared unique `uq_` as a constraint, fulltext `ix_…_fulltext`, spatial `gist_`; one `truncate_db_identifier` cap) from the entity model, the SQL generator and the kernel's renderer alike, and the name is recorded in `SnapshotIndex.name`, so a removal targets the name the database holds. An index `L` holds once under a name other than the one the rule gives it is renamed by one `INDEX_RENAMED` change the differ reports, applied as safe; one `L` holds in several copies is not a rename, and its surplus copies are undeclared removals.
- **The differ owns every comparison; a change carries its object.** `compute_snapshot_diff` is the one place `L` is compared with `D`, names and enum types included: a name-only difference is a rename and an enum type under a database name `D` declares no type under is an `ENUM_TYPE_REMOVED`. Every `SchemaChange` carries `subject`, the snapshot object of the one type `CHANGE_SUBJECT_TYPES` gives its kind (refused at construction otherwise); renderers and `convergence_outcome` read it, and `detail` is display text only.
- **Foreign keys are created, named once, explicit, and replaced when their actions change.** Every constraint is named by `datrix_rdbms_schema.foreign_key_naming` (`fk_<table>_<columns>`, the one identifier cap) from the snapshot builder, the SQL generator's DDL and junction tables alike; the name is recorded in `SnapshotForeignKey.name`, so a removal targets what the database holds. `render_schema` creates every key `D` records, and a key the converge adds is a `RELATIONSHIP_ADDED`, matched by the full columns / referred table / referred columns tuple (two keys to one table are ordinary); on an existing table it is applied as risky, validated over the rows, and an orphan row fails the apply, naming the constraint -- no row is deleted. Every constraint states `ON DELETE` and `ON UPDATE` through `sql_referential_action` (the DSL default is `restrict`). A key whose `onDelete`/`onUpdate` changed is one `FOREIGN_KEY_REPLACED` (risky, expand phase): the key is dropped under exactly the name `L` holds it by and `D`'s key added under `D`'s name -- on PostgreSQL `NOT VALID` then `VALIDATE CONSTRAINT`. A key `L` holds once under another name is one `FOREIGN_KEY_RENAMED`. A reflector (`datrix-codegen-sql` `dialects/`) records a live key's action through `dsl_referential_action`, so a reflected and a declared key compare action for action.
- **Every physical table the application uses is in the snapshot, once.** `RdbmsSchemaSnapshot.declared_tables()` is the one set `render_schema` creates and the differ reads: entity tables, CQRS read-model tables, audit-log tables and many-to-many junction tables. The audit-log table is declared once (`audit_log_table`; the SQL DDL is rendered from it, the trace-id column is always present); a junction table is derived once (`datrix_common.datrix_model.junction.junction_tables`: sorted-pair name, owning side, composite key, named `CASCADE` keys, reverse index) for the snapshot, the SQL DDL and every ORM's join table alike, and an entity related to itself is refused by name. A CQRS view model declares exactly the table-level index and unique rows the snapshot records for its table (never a column-level `index` flag; a column named only in a composite or unique row is not indexed on its own).
- **A change to an existing enum type is realized on every engine.** Appending a member and relabeling one are rendered by the kernel from `datrix_codegen_kernel.sql_facts.enum_member_change` and the dialect (`render_add_enum_value`, `render_rename_enum_value`): PostgreSQL through `ALTER TYPE … ADD VALUE` / guarded `RENAME VALUE`. Removing or reordering a member is never applied, with or without `--approved` (`REFUSED_CHANGE_KINDS`). A builtin call default (`= uuid()`, `= DateTime.now()`) is recorded as a `server_function` default, never a `literal`; every other default is a stored value recorded as a `literal`, on a `server` field too (`ScheduleStatus status : server = ScheduleStatus.Pending`, `Int version : server = 1`). Every default but a collection literal also records the SQL tree it lowers to (`SnapshotDefault.tree`), excluded from equality. Every statement stating a default renders it from the tree `D` records; a default without one is refused, never spelled from its text. A snapshot of any format version but `SCHEMA_VERSION` is refused with the instruction to regenerate it.
- **A block's SQL renders once, in the kernel.** `datrix_codegen_kernel.sql_facts.revision` returns a `RenderedRevision`: an ordered tuple of `SqlStatement`s, each carrying its `SqlStatementKind` (a closed set), the object it is about and its SQL. `render_schema(snapshot, dialect)` renders a whole schema from empty: the schema prelude (`render_create_schema`, `render_set_search_path` where the dialect `supports_feature("schema_namespaces")`), the named enum types (`named_enum_types`), every table, every foreign key (validated: the tables are empty), every check constraint, every index and column unique, the comments the dialect keeps out of `CREATE TABLE`, then the table triggers. `render_convergence(live, desired, changes, dialect)` renders the changes that bring a live catalog `L` to the declared schema `D`, behind the search-path prelude, in `schema_change_order`, with no whole-schema path: removals read from `L` under the names the database holds, additions from `D`, and `create_schema` in the prelude when `L` holds no table and no enum type (a catalog reader stamps the block's place on what it reads, so a schema the database lacks reads as one holding nothing; the dialect creates a schema only where it is absent) or the changes relocate the block into it. An empty catalog therefore renders the prelude and then all of `D`. Statements are unqualified; the schema is reached through the search path. Every `ChangeKind` is either rendered (`CHANGE_KIND_STATEMENT_KINDS`, the statement kinds it may produce, checked on every rendering) or refused with its reason (`REFUSED_CHANGE_KINDS`: a removed or reordered enum label); the two sets partition `ChangeKind`. A check (`ADD_CHECK_CONSTRAINT` for a schema's check or a `CHECK_ADDED`, `DROP_CHECK_CONSTRAINT` for a `CHECK_REMOVED`) is written from the lowered tree the snapshot records, by `datrix_rdbms_schema.sql_lowering.render.render_sql` for the block's DDL dialect, through the dialect's `render_add_check_constraint` / `render_drop_check_constraint`; a check with no tree (one a live catalog reflected) is refused when it would be created, and one whose SQL's digest is not the one its name ends in is refused, since its name no longer identifies its definition. A drop needs the name only. An `INDEX_RENAMED` renames the index `L` holds under the change's old name; an old name `L` does not hold is refused.
- `fulltext(...)` is realized on PostgreSQL only: a GIN index over the shared coalesce `to_tsvector` expression, which both languages' query step repeats verbatim. Any other engine is a generation error (`datrix_codegen_kernel.algorithms.fulltext_dialect`), never a differently-behaving index.
- `schemaConvergence { enabled }` per profile, default on: `false` leaves every RDBMS block of the profile out of the deploy's schema converge. Any other key in the block, and a `driftPolicy` section, is refused when the config loads.
