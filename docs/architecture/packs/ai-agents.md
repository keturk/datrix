# Pack: AI Agents — Model-Driven Tool Loops as a Declared Block

**Read when:** you touch the `agents` service block, `tool`/`agent` declarations, model providers, `approval`, `replay` fixtures, or agent observability signals.
**Not for:** the engineering agents that work on this repo (see `.claude/`).
**Core map:** [architecture-cheat-sheet.md](../architecture-cheat-sheet.md)

[Decision 46](../architecture-overview.md#decision-46-ai-agents--model-driven-tool-loops-as-a-declared-service-block-approved--implementation-in-progress) — Approved; Phases 1–2 implemented on Python and TypeScript (both realize the `MODEL` group and the `agents` domain); Phase 3 (`eval`, `ollama` image attachments, fixture capture, `cost` budgets) remains.

An `agents <alias> { model h; tool T(…) -> R : description('…') { ensure …; … } agent A(…) -> R { model(h); tools(…); steps(N); attachments(p); prompt { … } } }` service block: the author declares, the generator emits a bounded observe → decide → act → update loop. Provider, model id, sampling, timeout, key handle and budget live under the block alias in the service `.dcfg` (`provider` = API family, `flavor` = `container`/`external`/`managed`/`direct`).

- The model chooses only among declared tools (closed at generation); model-supplied arguments are untrusted input, parsed and checked by the tool's leading `ensure` clauses; tools run with the caller's identity; a model result is data, parsed against the declared type before use.
- Provider realization is a required per-provider platform declaration (absence is a construction error; no provider name in shared layers). Keys are logical secret handles; off-loopback transport is verified TLS unless `allowPlaintextHttp = true` with `auth = "none"`; no certificate-verification switch exists.
- `test` never reaches a live model (`replay` provider only, fixtures selected by `: replay('…')`). Every limit and budget field is realized before the call that would exceed it. Logs carry identity and counts, never content.
- Every language and platform is obligated (`MODEL` builtin group + `agents` domain) or carries a counted gap; the pre-generation realization stage rejects an `agents` block on a non-realizing language before any file is written. Python and TypeScript both realize them from one plan (`datrix_codegen_common.agents`); each declares its own provider and credential tables, so no provider name enters a shared layer, and a third language adds those two tables and a profile entry and changes no shared code.
- Where the libraries differ the behaviour does not: TypeScript's live clients are hand-built requests through `fetch` (`redirect: 'manual'`, no retry, no SDK, since a provider SDK reads the environment); its bulkhead is the runtime's `bounded-bulkhead.ts`, because cockatiel's cannot bound a wait in time; model-supplied values are read by the decorators a request DTO carries, with a stray top-level key refused first. Telemetry follows the service's metrics exposition on both languages (`agents_exposition`): `prom-client` or `prometheus_client` when scraped or undeclared, OpenTelemetry instruments when pushed.
- Parity is held by rows, not a probe of its own: `agents.parity.yaml` (`datrix/scripts/gates/parity/cases/`, fixture `agents`) reads the four approval routes through the existing `route_wire_contracts` on every registered language against authored expectations. The plan's equality is the comparison of `build_agents_context` under each language's profile (the `agents` row of `parity/domain_registry.py`), a budget field reaching emitted code is the perturb-and-diff kit, and a provider's wire contract is each language's own wire-byte specs. `problem-type-parity-gate` passes because both languages spell the families of `problem_map.py`; `ModelToolDenied`, `ModelToolArgumentInvalid` and `ModelApprovalPending` disclose the registered title only, and a pending answer carries its `requestId`.
- Phase 2 added the fail-closed `approval` marker (suspended run behind an injected request row — the compare-and-set contract — four role-gated endpoints, deciding principal never the requester, continuation declared on the agent), managed model placement on AWS/Azure, model calls as a resilient-client dependency kind, and agent signals on the five observability categories. Cost budgets stay rejected; live-turn fixture capture is out of scope.
- An app decides through `<Service>.ApprovalAPI` (`requests`, `request`, `approve`, `deny`) when `approvals.exposure = "public"`: `datrix_common.approvals.client_api` attaches that view as `Service.approval_client_api`, beside `rest_apis` and not in it, because the language's approval runtime emits those routes. Client-call resolution and the client contract read `client_rest_apis()`; code emitting a service's own routes reads `rest_apis`. With `internal` there is no such API, and a call to it is refused like any unknown API.
- A service with an approval tool may `catch (ModelApprovalPending e)` around an agent call to answer its own caller normally; uncaught, the route answers `202` with `requestId`. The row is already committed when it is raised, so the agent is called outside every `transaction`: `AGT008` refuses a `transaction` body whose reach includes an agent naming an approval tool, on every language.
- A tool's `ensure` clauses check only its arguments: they run with no database session and no request identity. A check of who owns what goes in the tool body, which runs under the original caller's principal after approval: `Auth.userId()`, `Request.userId()` and audit stamps name the requester, and any read that needs claims (`Auth.identity`, `Auth.token`) is refused, because a resumed run holds no token.
