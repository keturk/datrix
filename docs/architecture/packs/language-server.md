# Pack: Language Server (LSP) and Editor Client

**Read when:** you touch `datrix-language/src/datrix_language/lsp/`, `datrix lsp`, the keyword manifest, `.dtrx`/`.dcfg`/`.dseed` editor features, or `datrix-vscode`.
**Not for:** the parser or semantic analyzer themselves.
**Core map:** [architecture-cheat-sheet.md](../architecture-cheat-sheet.md)

[Decision 41](../architecture-overview.md#decision-41-datrix-language-server--editor-intelligence-over-lsp-adopted) — Adopted.

LSP for `.dtrx`/`.dcfg`/`.dseed` (diagnostics, completion, hover, definition, references, symbols) in `datrix-language/src/datrix_language/lsp/`, launched by `datrix lsp` (optional `datrix-language[lsp]` extra, imported lazily). It never runs generation, generator/platform discovery, or a formatter; analyzes an application at most once per text version; analyzes only structurally complete parses; publishes diagnostics per owning file; routes a document by the parser's own suffix map (`DOCUMENT_KIND_BY_SUFFIX` in `parser/document_kinds.py`, read by `lsp/workspace.py`'s `document_kind_of`), so the editor and the toolchain agree on what every file is, and every routed kind has a service (a test compares the two sets); has one home per language vocabulary (generated keyword manifest feeds completion and the editor grammars; `.dtrx`, `.dcfg` and `.dseed` keywords come from the terminals of tree-sitter's generated `grammar.json` — every `STRING` outside a lexical `TOKEN` — read through the parser's freshness contract so a stale or missing artifact raises, never from `grammar.js` text; one grammar holds the model, config and seed documents, so each language reads only the rules its own document root reaches (`_top_level_element` for `.dtrx`, `config_document` for `.dcfg`, `seed_document` for `.dseed`); delimiters come from the `DTRX_*` constants beside `grammar.js`, which lexes all three languages (`.dcfg` and `.dseed` without a doc-comment channel: neither transformer publishes a comment); a platform's contributed `.dcfg` block key is refused when it is not an identifier or is a keyword that can begin a profile item, so it can always be written as a block name); uses stdio only and runs no workspace-supplied code; bounds untrusted input (4 MiB documents of every kind, refused by `WorkspaceStore` before any parse; `.dcfg` and `.dseed` nesting at 64 levels, enforced by the parsers themselves, so the CLI path carries the same bound); cannot navigate outside the workspace; carries no document content in logs or diagnostics; resolves `datrix lsp` from the user's `PATH` only. `.dcfg` gets exactly what its fail-fast, location-free AST supports (one syntax diagnostic per file, inbound navigation, highlighting). `.dseed` gets the same bounded support from its fail-fast front end: `lsp/seed_documents.py` parses with `SeedParser`, never raises, and publishes at most one `SEED_PARSE` diagnostic, sanitized like every parser message (a seed message names no cell value), plus highlighting; no index, no position features.

**Where its answers are tested.** A hover, completion or definition answer is a fixture annotation (`// @hover`, `@complete`, `@definition`) at a `$0` cursor in the language package's dedicated `tests/fixtures/cases/lsp-*` projects, run by its case runner; server lifecycle, workspace and limits stay code tests.

**Unsaved buffers.** A `.dtrx` analysis reads every file it pulls in through one workspace overlay (`lsp/overlay.py`): the open editor buffer when there is one, saved or not, and disk otherwise. That covers both the included `.dtrx` files and every `.dcfg` the application uses (the system config, each service, shared and extern config, and any config those import) — the overlay backs the `DcfgDocumentSource` attached to the freshly parsed application. Parse, config resolution, pre-analysis injection and semantic analysis run inside one `track_reads()` block, and every path read there becomes an edge in the include graph, replaced on each analysis. A `didChange` or `didClose` on any of those files then re-analyzes the open entry documents that read it in the same event, so an unsaved `.dcfg` edit (a dropped port, say) shows on the `.dtrx` immediately and closing the buffer without saving republishes from the file on disk. The overlay serves only buffers the user opened and resolves no path the loaders would not; on disk it counts only a regular file, so a directory at a config path reads as a missing config. A `.dcfg` that cannot be read or decoded degrades to the service's own config diagnostics, never an internal error.

**Grammar fields.** `grammar.js` labels the children of most declarations with tree-sitter `field()` names spelled as the model fields they fill (`name`, `syncs_entity`, `parameters`, `is_abstract` over the `abstract` keyword); the transformer's generic builder reads them (`datrix-language/docs/architecture/parser-overview.md`, *Field-driven building*). A label is not a terminal: it adds no keyword to the manifest, and it changes neither node types nor child order, so the LSP's type-based CST walks stay valid. A walk that needs one child may read it by field (`node.child_by_field_name("name")`) instead of by position.

**datrix-vscode** is the TypeScript client: no `pyproject.toml` (absent from the venv and Python scans), a Node test suite run by `test.ps1`. It registers the `dtrx`, `dcfg` and `dseed` languages, each with a language configuration, a TextMate grammar generated from the manifest (`scripts/generate-grammars.mjs`, whose one `GRAMMAR_TARGETS` list the freshness check also reads; tests hold it equal to the manifest's languages and to `package.json`'s grammar contributions), an activation event and a client document selector. It consumes the keyword manifest of `datrix-language` through a subprocess contract no import scan sees, declared in `datrix/scripts/config/cross-ecosystem-dependencies.json`, because the packaged `.vsix` must name no framework package; `verify-package-contents.mjs` also refuses any `.dtrx`, `.dcfg` or `.dseed` file in the archive.
