# Pack: Generated Runtime and Deploy — Boot Path, Zero-Environment, Headers, Gateways, Observability

**Read when:** you touch what a generated service does at startup or on the wire: readiness probes, the secret backend, env-var handling, `.gitignore` of a generated project, framework HTTP headers, RFC 7807 problem types, gateway realizations, or observability providers.
**Not for:** migration state ([migrations.md](./migrations.md)) or auth semantics ([auth.md](./auth.md)).
**Core map:** [architecture-cheat-sheet.md](../architecture-cheat-sheet.md)

## Boot-Path Contracts

[Decision 45](../architecture-overview.md#decision-45-a-generated-service-must-be-able-to-reach-its-database--probe-transport-migration-readiness-and-chain-owned-schema-approved--implementation-in-progress) — Approved, implementation in progress.

A service that compiles is not a service that runs. Rules, each an executable comparison: a readiness probe exercises the transport its dependents connect over (`service_healthy` releases dependents on the probe's word); a probe command has one home and zero-consumer registries are deleted; every target's migration entrypoint waits for the database over a bounded retry (one shared attempt-count + delay) before any DDL; a migration failure reports the driver's diagnosis (credential-free URL); every type an emitted migration references is created by that same chain (`referenced − created` empty); a native type's name has one home per language and its labels one home for all (`enum_member_stored_literal`); schema DDL is never emitted outside the migration chain (no init-script DDL); an unrecognised migration operation kind raises; no service resolves a connection fact or credential from the process environment; a declared secret backend with no renderer raises rather than falling back to an environment reader. Migration specifics: [RDBMS Migration Decisions D39–D41](../rdbms-migration-decisions.md#boot-path-readiness-and-chain-owned-schema-d39d41).

## Zero-Environment Runtime

Every deployment-static value is baked at generation time; a running service consults no environment variable. Each language carries `LanguageCapabilityDeclaration.zero_environment_runtime` (regexes spelling an env read in its templates); a language not realizing it carries a counted `capability_gaps` row. `zero-environment-runtime-gate.ps1` censuses every language's templates (a realizing language fails on an unlisted/stale exemption in `zero-environment-runtime-baseline.json`; a gap-row language carries a decrease-only read count). A missing value is never defaulted.

## Shared Cache Consumption

A service `uses` a shared cache container with an access: read by default, `readwrite` to write (`datrix_common.datrix_model.shared_block_access`). `realized_cache_blocks(service)` (`shared_cache_scope`) is the one derivation of the cache blocks a service realizes: its own (owned) then each consumed shared block (the owner's own node, never a copy). The **ambient** cache (`Cache.*`, `@cache`, rate limiting) stays the service's own block (`service.cache_block`, or the synthetic rate-limit connection) and never binds a consumed one. Every connection-bearing surface walks the realized set: `derive_connection_surface`, each language's per-block connection module, settings field (`<block>_redis_url`) and health check, each platform's seeded connection keys, network reach and access grants.

**One key namespace, the owner's** (`cache_key_namespace`): a service's own blocks keep `ServicePaths.service_dir`, a shared block's is the snake form of the shared container's name, so a reader computes the keys a writer set. A shorthand `Entry.method(...)` call resolves only when exactly one realized block declares the entry (CCH003 otherwise).

**One operation vocabulary** (`datrix_common.cache.operations.CACHE_ENTRY_OPERATIONS`, `(kind, method, arity) → READ | WRITE`): every language's dispatch table has exactly its key set, and a block realized with read access emits read-only typed methods and no decorators (SHR010 rejects a write in a body). TLS is one rule, `redis_url_scheme` (`rediss` exactly when the platform's cache identity is managed Entra).

**Platforms.** Docker points a consumer at the **owner's** container (its wait, its `cache` network, its owner-wide database index). AWS keeps the cluster's security group closed and has each consuming stack add an explicit security-group-to-security-group ingress and egress. Azure's Redis module takes `accessPrincipals` (one assignment per consumer web app and function app) and a consumed block's backend entry names the owner's `existing` instance. A pooled consumed block is realized on docker and Azure; AWS fails closed (the pool has no single home stack). Each platform proves it wrote every connection key the surface declares for the blocks it provisions (`require_cache_keys_supplied`), naming every miss in one raise. `shared-cache-realization-gate.ps1` holds every registered language and platform to the realized-block walk.

## Untracked Project Artifacts

A service reads, and is granted, exactly the secrets its model derives. `service_secret_reads` is the one read set; `build_application_secret_placement` gives each secret an owner (service, shared container, application), a store and one rendered name; the provisioner, the language's resolver manifest and every platform grant read that placement (Azure: a vault per service plus the application vault, per-secret grants on shared secrets; AWS: exact-ARN grants; docker: files mounted per service, application-owned ones under `secrets/_application/`). Every language renders its resolver from one `SecretResolverPlan` keyed on `SecretBackendPolicy.default_backend`, and a plan a resolver could not read is a generation error. Framework key pairs are never shipped: on docker `scripts/deploy.py` generates a missing pair on the deploying machine (`GENERATE_OWNED_KEYPAIR_IF_MISSING`); cloud platforms seed them through the deploy-time identity. Detail: the kernel's `secret-render-contract.md`.

A generated `.gitignore` has two owners: the language's `service/gitignore.j2` (toolchain leftovers only) and the platform-declared `PlatformCapabilityDeclaration.untracked_project_artifacts` (pattern + reason; docker's `secrets/*/` and compose `.env`, Azure deploy transcripts), resolved by `capability_resolution.untracked_project_artifacts_for(provider, runtime)` and appended by the shared `DocGenerator` (`datrix_codegen_kernel.generation.project_ignore`). A language template never re-types a platform's secret layout.

## Framework HTTP Headers and Problem Types

**The caller's address is a declared platform fact** (`client_address` family: `X-Datrix-Client-Address`). Each platform's `PlatformCapabilityDeclaration.client_address_source` states, per runtime and ingress, whether the connection peer is the caller (`TRANSPORT_PEER`), N trusted proxies append to `X-Forwarded-For` (`FORWARDED_FOR`), or the system gateway overwrites the framework header (`GATEWAY_ASSERTED`, trusted only under a stated provenance: a network-isolated gateway or a verified trusted-caller stage). Every system gateway realization (nginx, API Management, API Gateway REST and HTTP) overwrites the header with the peer it saw, so a client's own value never passes. `datrix_codegen_common.generation.client_address_plan` turns the declaration into one plan, and each language renders the one resolution rule from it (python's inlined `client_address.py`, TypeScript's `src/common/client-address.ts`): a header is read only for a request that provably came through the declared proxy; every other case and every failure falls back to the connection peer (never forgeable, possibly coarse). The anonymous rate-limit key, the request log's `client_address` field and `Request.ip()` all read it; no language keeps a private reader, and every launch site turns the application server's own proxy-header handling off (`SERVER_PROXY_HEADERS_ENABLED`). A forwarded entry may carry the port its proxy appended (`ip:port`, `[ipv6]:port`), which is dropped; with the platform front end as the only ingress the forwarded header is read even when there is no connection peer. **A serverless endpoint hosted off the container runtime** (Lambda, Azure Functions) resolves by its host's own declared source, `PlatformCapabilityDeclaration.serverless_http_client_address` (required exactly when `serverless_compute_model` is not `CONTAINER`; `TRANSPORT_PEER` or front-end-only `FORWARDED_FOR`, never a gateway assertion, because no serverless host runs a trusted-caller stage): AWS hands the API Gateway event's `requestContext` source address over as the peer, Azure reads the right-most `X-Forwarded-For` entry its front end appended. `build_serverless_client_address_plan` reads the source of the block's resolved host from every installed platform realizing it (they must agree). Every serverless HTTP adapter (Lambda and Functions, in each language) binds its invocation as the active request for the whole call with that resolver, so `Request.*` and `Auth.*` reached from the handler — directly in an endpoint body or through a service function — answer exactly as on the REST route; a job, subscription or queue-consumer body serves no request, so a request read there is refused at generation.

**The trusted-caller token is a declared platform fact.** A platform whose managed gateway forwards a caller token declares `PlatformCapabilityDeclaration.trusted_caller` (`TrustedCallerTokenProfile`: the claim naming the caller, how a peer mints, and the lifetime a minter requests) and must deliver the audience, issuer and admitted-principal settings; `service_trusted_caller_profile` and `service_has_trusted_caller_outbound` (kernel) decide, for every language and platform, which services verify and which mint. Every verifier finds the issuer's keys through its OpenID discovery document and admits the declared claim; the gateway and every calling peer mint with their own identity (Azure: managed identity, `oid`; AWS: STS web identity token, `sub` = the role ARN, minted by the gateway's Lambda authorizer and each calling service's task role). A platform declaring a profile without a minter at its gateway is a defect its own seam test catches. Verification fails closed: a missing token, an issuer or key set not served over HTTPS, a discovery document naming another issuer, or a principal outside the admitted set refuses the request; only an accepted token marks the request as having come through the verified gateway, and only that mark lets the client-address resolver read the gateway's asserted header.

Every header Datrix mints (trusted-caller token, rate-limit headers, inbound webhook secret, outbound delivery headers) has one home, `datrix_codegen_common.generation.http_headers` (`FRAMEWORK_HEADERS`; retired names under `RETIRED_HEADERS`); a language uses the exact registered name or constant and is obligated to realize every family. `framework-header-parity-gate.ps1` (exemptions in `framework-header-exemptions.json`, empty today; retired spellings have no exemption path). An undeterminable token-revocation status is its own family, `revocation-unavailable` (503 with `Retry-After`), so a client never mistakes a down revocation store for a refused credential; the same condition closes an open socket 1013. RFC 7807 `type` values are `urn:datrix:error:<slug>`, minted only by `datrix_common.datrix_model.problem_types` (`FRAMEWORK_PROBLEM_TYPES`). **A language never spells one:** every refusal a generated service writes — a route, a guard, a middleware, a serverless adapter, a websocket or GraphQL denial — goes through that language's one registry-rendered responder (`problem_details.py` / `problem-details.dto.ts`) by `PROBLEM_<FAMILY>` reference, and `problem-type-parity-gate.ps1` counts registry references, fails any `urn:datrix:error:<slug>` literal, and holds every family to referenced-or-counted-gap.

| A request is refused because | Answer |
|---|---|
| a body is not JSON, is absent, or its top level is not the declared kind | 400 `bad-request`, fixed detail |
| a path / query / body field is missing, unknown, repeated (a scalar query key sent twice) or of the wrong shape | 422 `request-validation`, `errors[]` of `{location, field, code, message}` with `location` ∈ `path`/`query`/`body` and `code` ∈ `required`/`unknown_field`/`repeated`/`invalid` — one entry per field, the highest-precedence code |
| an entity `validate` block fails | 422 `validation`, `violations[]` |
| a delete meets a `restrict` child | 409 `cascade-restriction`, checked before any before-hook runs on both languages |
| a caller is unauthenticated, forbidden, throttled or a dependency is down | 401 / 403 / 429 / 503 with the registered title only — the reason code is logged, never sent |

The trusted-caller refusal is opaque on the wire and writes the shared audit event `identity.trusted_caller.rejected` (`reason_code`, `path`) on both languages.

## Gateways and Observability

- **Declaration-driven gateways** (NGINX, Azure APIM, AWS API Gateway), emitted when the system declares `gateway { }`. All consume the one shared route enumeration (`datrix_codegen_kernel.generation.gateway_routes`), so the public surface (including nested sub-collection routes) and per-route edge credential policy cannot diverge. A GraphQL HTTP path is EXACT, the subscription path `<basePath>/subscriptions` is an upgrade route, and a path published by two gateway services fails generation. **Gateway-minted routes no backend serves are a declared family registry** (`GATEWAY_SYNTHESIZED_ROUTE_FAMILIES` → `gateway_synthesized_routes`: health-probe and OpenAPI discovery/spec families); registering a family reaches every target, and a platform's private route table never mints one. Every realization forwards a request's public path to the service unchanged: a parameterized route's AWS REST greedy `{proxy+}` resource (ECS NLB and App Runner alike) puts its literal prefix back in front of `{proxy}`, which API Gateway binds to the path below the resource only. A GraphQL subscription path (`<basePath>/subscriptions`) is its own APIM WebSocket-passthrough API on both Azure topologies (App Service and azure-vm), never at a GraphQL HTTP path (held by a set comparison in the Azure suite), and any APIM diagnostic resource a template adds must mask the `subscription-key` query parameter (`dataMasking.queryParams`), held by a guard over every rendered APIM module.
- **Native-only observability per platform** — each target emits only its native providers (LOCAL: Prometheus/Jaeger/Loki/Grafana/Alertmanager + cAdvisor and alert rules; AWS: CloudWatch/X-Ray; Azure: Azure Monitor/App Insights). Each platform declares its set on `PlatformCapabilityDeclaration`; a generic validator rejects non-native providers (Decision 27). Export volume and diagnostics are separate portable axes ([parity-and-obligation.md](./parity-and-obligation.md)).
- Jobs run on a schedule or on demand through `dispatch Job();`, realized as a framework-owned queue and consumer: the semantic analyzer synthesizes one builtin queue and one builtin same-service consumer per dispatched job, so every registered language, engine and platform provisions it exactly as it does an author's self-consumed queue, and the consumer runs the job's own timeout/retry/dead-letter wrapper.
- Other shipped capabilities: background jobs (APScheduler), seed data, Elasticsearch, GraphQL DataLoaders, rate limiting (gateway + per-route Redis), RFC 7807 errors, inter-service HTTP auth, ArcGIS FeatureServer paged ingestion (`arcgisFeatureLayer` integration kind).
