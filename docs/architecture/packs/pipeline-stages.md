# Pack: Generation Pipeline Stages, Builtins, Stdlib Load Order

**Read when:** you add, remove, reorder or debug a `GenerationPipeline` stage; touch builtins or stdlib loading; or ask "where in the run does X happen?".
**Not for:** what any one generator emits.
**Core map:** [architecture-cheat-sheet.md](../architecture-cheat-sheet.md)

**Builtins and stdlib:** builtins (traits, scalars, enums, the four builtin domain exceptions in `builtins.dtrx`) ship as pre-parsed ASTs. Seven stdlib `.dtrx` modules ship under `datrix-language/src/datrix_language/` (the directory is named through `StdlibParserProtocol.stdlib_module_directory`); the loader in `datrix_common.stdlib` parses them once into module ASTs that stay lazy. User files go through Tree-sitter + transformers into `Application`. **Load order:** builtins → stdlib placeholder registration → user parse/transform → semantic analysis (a stdlib module deserializes on its first resolved reference).

`GenerationPipeline` lives in `datrix-cli/src/datrix_cli/pipeline/generation.py`; `run()` walks an ordered registry of typed `Stage` values. Stages, in order: `parse` → `attach_config_documents` → `discover_and_parse_seeds` → `resolve_service_configs` → `inject_identity_system_entities` → `inject_approval_system_entities` → `inject_push_device_registry` → `analyze` → `apply_service_filter` (skipped without `--service`) → `validate_deployment` → `resolve_incremental` → `build_codegen_context` → `build_deployment_plan` → `resolve_config_surfaces` → `discover_generators` → `validate_type_completeness` → `validate_builtin_realization` → `discover_platforms` → `sort_generators` → `select_generation_targets` (skipped without `--only`) → `attach_runtime_bootstrap` → `generate:{name}` (per generator) → `resolve_intra_group_conflicts` → `detect_file_conflicts` → `assert_deploy_binding_conformance` → `write:{target}` (per target) → `migrations` → `discover_language_hooks` → `run_language_post_processing` → `run_client_target_post_processing` → `format_json_files` → `update_append_only_hashes` → `snapshot` → `commit_migration_state`.

`attach_config_documents` sets `Application.config_documents` to a `DcfgDocumentSource` over disk (datrix-language). Every `.dcfg` the run reads — system, service, shared, app, extern, identity and strings configs, and every file they import — is read through that source and parsed at most once; a loader reached through an application without one raises `ConfigDocumentSourceMissingError`. `datrix validate` and the CLI's `resolve_application` attach the same source after their own parse.

Infrastructure-config resolution and memory-limit normalization are **not** stages: they run inside `analyze` as `SemanticAnalyzer.analyze()` pre-seal hooks. There is no `platform_validation` or `apply_cli_overrides` stage; `--language` is resolved before the run, and `(provider, DeploymentProvider)` realization checks run in the pre-seal infrastructure hook.

**Where the stages' code lives.** The CLI names and times the stages; two of their families are owned below it, so every caller runs the same code:

- **Pre-analysis** (`discover_and_parse_seeds` … `inject_push_device_registry`) is `datrix_semantic.pre_analysis.PRE_ANALYSIS_STEPS`, an ordered tuple of named steps over `(Application, PreAnalysisInputs)` (project directory, source, profile, seed parser — the parser a `datrix.parsers` entry point supplies). `run()` registers one stage per step, named after it. `analyze_with_pre_seal_hooks` folds the infrastructure resolution into analysis; `inject_identity_system_entities` fails loud: a provider `.dcfg` it cannot resolve raises `GenerationError` naming the provider, its path, the app directory and the profile. `prepare_and_analyze` runs every step and then analysis, and is what `datrix validate`, the commands that read an analyzed application (`_app_spec.resolve_application`) and the test harness (`datrix_testing.project.analyzed_project`) call — so `datrix validate` parses and validates the project's seed documents exactly as generation does. Seed files are found by `datrix_common.seed.discovery.discover_seed_files`, which `datrix seed` uses too.
- **Run context** (`build_codegen_context` → `build_deployment_plan` → `resolve_config_surfaces`, then `attach_runtime_bootstrap`) is `datrix_codegen_kernel.generation.run_context`: `build_codegen_context`, `DeploymentPlan.resolve`, `resolve_config_surfaces`, `attach_runtime_bootstrap`, and `normalize_service_memory_limits` (the pre-seal hook `analyze` adds for the target language). `resolve_run_context` runs the first three as one call; tests reach it through `datrix_testing.project.generation_inputs`.

`commit_migration_state` stays in the CLI: it ends a real run and writes the ledgers.

Why these homes: the pre-analysis steps read only `datrix-common`, `datrix-semantic` and a parser, and the run-context steps only `datrix-common`, the kernel and `datrix-migration`. The test harness cannot import `datrix_cli` (every package, the CLI included, takes `datrix-testing` as a `dev` extra, so the edge would be circular), and the kernel loads no semantic module, so the pre-analysis composition cannot live there either. A test-side copy of either half is never the answer: each such copy drifted from the CLI (no seed discovery, no identity injection, a context that defaults the deployment whatever the fixture says).
