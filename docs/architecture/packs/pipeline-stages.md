# Pack: Generation Pipeline Stages, Builtins, Stdlib Load Order

**Read when:** you add, remove, reorder or debug a `GenerationPipeline` stage; touch builtins or stdlib loading; or ask "where in the run does X happen?".
**Not for:** what any one generator emits.
**Core map:** [architecture-cheat-sheet.md](../architecture-cheat-sheet.md)

**Builtins and stdlib:** builtins (traits, scalars, enums, the four builtin domain exceptions in `builtins.dtrx`) ship as pre-parsed ASTs. Seven stdlib `.dtrx` modules ship under `datrix-language/src/datrix_language/` (the directory is named through `StdlibParserProtocol.stdlib_module_directory`); the loader in `datrix_common.stdlib` parses them once into module ASTs that stay lazy. User files go through Tree-sitter + transformers into `Application`. **Load order:** builtins → stdlib placeholder registration → user parse/transform → semantic analysis (a stdlib module deserializes on its first resolved reference).

**Builtin members: one definition each.** Every builtin member (`Http.get`, `Log.info`, an extension's objects included) has one definition in `datrix-common`, a `datrix_common.builtins.meta.Builtin` subclass, which declares its identity, signature and arity; `datrix_common.builtins.definitions.builtin_definitions()` is the one reader (it loads every installed extension's objects first). `BUILTIN_REGISTRY` (`datrix_codegen_common.transpiler.builtin_registry`) keeps only emission metadata keyed by `(category, member)`: a row's arity and result type are read from the definition, never restated. `definition_registry_problems()` is the two-way set comparison between the registry's keys and the definitions' members: a row no definition declares, a definition member with no row (a `GeoSql` query predicate, realized by each language's query lowering, is the one member with no row), and a query predicate carrying a row are each a problem. A test holds it (`test_builtin_realized_arity.py` in `datrix-codegen-common`); it never runs at import, because reading the definitions loads every installed extension pack.

**Body analysis: resolutions first, facts derived from them.** Inside `analyze`, six semantic phases handle executable bodies (a `fn`, a test, an agent prompt, an event `ensure`, a computed field), in this order:

| Phase | Produces |
|---|---|
| `resolve_code_bodies` (`datrix_semantic.bodies.resolve`) | a resolved `Ref` on every name a body uses (identifier, qualified name, member access, call, struct literal): the declaration, builtin member or query root it names, and whether it is a write. Reports VAR001–VAR003 and BODY_TYPE001 |
| `validate_code_bodies` (`datrix_semantic.code_body_validator`) | diagnostics only; a consumer of the recorded references, it derives nothing |
| `derive_callable_effects` (`datrix_semantic.bodies.effects`) | each callable's `CallableFacts` (`facts`): its own effects (14 `EffectKind`s), its callees, its transitive reach (shared by every callable of a cycle), its reads, locals, interpolation count, builtin uses, whether it returns a value, and its integration calls (`IntegrationCall`: each `Client.method(...)` whose receiver resolved to a configured integration client, with the client, the method and the call node, in body order) |
| `derive_reads` (`datrix_semantic.bodies.reads`) | whether each binder (local, parameter, lambda parameter) is read |
| `stamp_cross_service_contracts` (`datrix_semantic.named_call_type_annotator`) | the `EndpointContract` each resolvable cross-service call of a service's bodies names, stamped on the call from the cross-service contract registry (read with `datrix_common.cross_service.contract.get_cross_service_contract`) |
| `derive_service_usage` (`datrix_semantic.bodies.usage`) | each service's `ServiceUsage`: the builtins it calls and reads, the events and queues it dispatches, the integrations, structs, enums and constants it references, its revocation needs, its locals and called functions, and the stamped contract of every cross-service call it makes (`cross_service_contracts`) |

`datrix_semantic.bodies.analysis.analyze_bodies` runs the producing phases in the same order for a model built outside the analyzer (the test helpers in `datrix_testing.body_facts` call it); before stamping it lowers the auth contracts and builds the contract registry, as the analyzer's earlier phases do. Facts are recorded only on owners of those body kinds; a client declaration body carries none.

**Client-app expressions are resolved by their slot.** Every expression a client-app declaration holds outside a `fn` -- a `state` initializer, a `data` binding, a view condition or iterable, a view element's arguments and modifiers, a table's source, empty action and members, a form's submit, lifecycle and members, a workspace section's members, a nav link's modifiers, a page's `meta`, a style's and a theme's values -- is one client-declaration body, and each of its roots has a slot in the one table `datrix_common.datrix_model.ui_vocabulary` (`iter_ui_roots`, `UiSlot`). A `CODE` slot (an element's text, an event slot, `bind(...)`, a column's `label(...)`) resolves as code in the owner's scope, with each enclosing `foreach` variable, an item template's `item`, and the names its own position binds (`item`/`column` of a data element's event slot, `row` of a table's row action: `UiSlotBinding`). Every other slot is a word of the UI vocabulary and resolves to what it names (`datrix_semantic.bodies.ui_names`): a page or workspace section, an image asset, a form or table, a component or a style of the app (its `extends` chain applied); a token of its effective theme (`ThemeToken`: a style's token reference, a breakpoint, a tone); a `Fmt` member (a column's `format(...)`); or a term of a closed vocabulary (`UiVocabularyTerm`: an icon glyph, a chart kind, an action kind, a client target, `auto`, a theme value constructor). A word naming nothing is never VAR001: its slot's own UI check reports it. A module's UI declarations resolve their own members, components and styles only; their app copies resolve in each importing app. The inventory's totality test proves no client-app expression escapes this table.

Generators read what analysis recorded and never walk a body to learn it. The reads are, and are only:

| Module | Reads |
|---|---|
| `datrix_common.datrix_model.resolution` | `resolved_target(node)`, `resolution_ref(node)`, `is_write(node)`, `has_resolution(node)` (analysis-time walks only) |
| `datrix_common.datrix_model.effects` | `callable_facts(owner)`, `reached_functions(service, also_from)`, `effects_of_kinds`; `CallableFacts.reached_kinds`, `reached_subjects`, `own_subjects`, and the recorded fields `callees`, `reads`, `builtin_uses` and `integration_calls` |
| `datrix_common.datrix_model.usage` | `service_usage(service)`; `ServiceUsage.calls_category`, `ServiceUsage.cross_service_contracts` |
| `datrix_common.datrix_model.reads` | `is_read(binder)`, `is_read_beyond_rethrow(clause)`, `assignment_writes_unread_local`, `outer_binder_use`, `binder_name`, `read_lambda_parameters` |
| `datrix_codegen_common.algorithms.service_body_owners` | `entity_body_owners`, `realized_entity_body_owners`, `service_reached_functions` |
| `datrix_codegen_common.transpiler.async_realization` | `AsyncRealization`, `callable_is_async`, `SYNCHRONOUS_REALIZATION`, `awaiting_builtin_calls` |

Every read is total: a node analysis did not resolve, or an owner that carries no facts, raises `GenerationError` rather than answering a default, because a reader that guessed would be a second resolver. A call site binds the function analysis resolved its target to, never a function found by spelling.

`GenerationPipeline` lives in `datrix-cli/src/datrix_cli/pipeline/generation.py`; `run()` walks an ordered registry of typed `Stage` values. Stages, in order: `parse` → `attach_config_documents` → `discover_and_parse_seeds` → `resolve_service_configs` → `inject_identity_system_entities` → `inject_approval_system_entities` → `inject_push_device_registry` → `analyze` → `apply_service_filter` (skipped without `--service`) → `validate_deployment` → `resolve_incremental` → `build_codegen_context` → `build_deployment_plan` → `resolve_config_surfaces` → `discover_generators` → `validate_type_completeness` → `validate_builtin_realization` → `discover_platforms` → `sort_generators` → `select_generation_targets` (skipped without `--only`) → `attach_runtime_bootstrap` → `generate:{name}` (per generator) → `resolve_intra_group_conflicts` → `detect_file_conflicts` → `assert_deploy_binding_conformance` → `write:{target}` (per target) → `discover_language_hooks` → `run_language_post_processing` → `run_client_target_post_processing` → `format_json_files` → `update_append_only_hashes` → `snapshot` → `commit_migration_state`.

`attach_config_documents` sets `Application.config_documents` to a `DcfgDocumentSource` over disk (datrix-language). Every `.dcfg` the run reads — system, service, shared, app, extern, identity and strings configs, and every file they import — is read through that source and parsed at most once; a loader reached through an application without one raises `ConfigDocumentSourceMissingError`. `datrix validate` and the CLI's `resolve_application` attach the same source after their own parse.

Infrastructure-config resolution and memory-limit normalization are **not** stages: they run inside `analyze` as `SemanticAnalyzer.analyze()` pre-seal hooks. There is no `platform_validation` or `apply_cli_overrides` stage; `--language` is resolved before the run, and `(provider, DeploymentProvider)` realization checks run in the pre-seal infrastructure hook.

**Where the stages' code lives.** The CLI names and times the stages; two of their families are owned below it, so every caller runs the same code:

- **Pre-analysis** (`discover_and_parse_seeds` … `inject_push_device_registry`) is `datrix_semantic.pre_analysis.PRE_ANALYSIS_STEPS`, an ordered tuple of named steps over `(Application, PreAnalysisInputs)` (project directory, source, profile, seed parser — the parser a `datrix.parsers` entry point supplies). `run()` registers one stage per step, named after it. `analyze_with_pre_seal_hooks` folds the infrastructure resolution into analysis; `inject_identity_system_entities` fails loud: a provider `.dcfg` it cannot resolve raises `GenerationError` naming the provider, its path, the app directory and the profile. `prepare_and_analyze` runs every step and then analysis, and is what `datrix validate`, the commands that read an analyzed application (`_app_spec.resolve_application`) and the test harness (`datrix_testing.project.analyzed_project`) call — so `datrix validate` parses and validates the project's seed documents exactly as generation does. Seed files are found by `datrix_common.seed.discovery.discover_seed_files`, which `datrix seed` uses too.
- **Run context** (`build_codegen_context` → `build_deployment_plan` → `resolve_config_surfaces`, then `attach_runtime_bootstrap`) is `datrix_codegen_kernel.generation.run_context`: `build_codegen_context`, `DeploymentPlan.resolve`, `resolve_config_surfaces`, `attach_runtime_bootstrap`, and `normalize_service_memory_limits` (the pre-seal hook `analyze` adds for the target language). `resolve_run_context` runs the first three as one call; tests reach it through `datrix_testing.project.generation_inputs`.

`commit_migration_state` stays in the CLI: it ends a real run and writes the ledgers.

**Incremental generation: what a service's digest reads.** `resolve_incremental` compares each service's input digest (`datrix_common.datrix_model.content_digest`) with the last run's. It only decides whether the run generates at all: when nothing changed the run stops there, and otherwise every generator reads the whole Application — never a copy narrowed to the changed services, since application-level artifacts describe every service and each target's obsolete-file cleanup prunes what a run does not emit. The facts analysis derives from a body's resolved names (`facts`, `is_read`, `is_read_beyond_rethrow`, `read_parameters`, `body_usage`, `interpolations`, `outer_reads`, `outer_length_reads`, `outer_writes`) are not inputs: they restate what the digested bodies already say, so `_NON_INPUT_NODE_ATTRIBUTES` skips them, with `parent`, the seal flag and the source-position fields. A body's resolution `Ref`s are inputs: each digests as the name and the label of the declaration it resolves to, and a target in another top-level container (a module, a shared container) adds that container to the digest's references, so a change there changes the digest of the service whose body names it.

Why these homes: the pre-analysis steps read only `datrix-common`, `datrix-semantic` and a parser, and the run-context steps only `datrix-common`, the kernel and `datrix-migration`. The test harness cannot import `datrix_cli` (every package, the CLI included, takes `datrix-testing` as a `dev` extra, so the edge would be circular), and the kernel loads no semantic module, so the pre-analysis composition cannot live there either. A test-side copy of either half is never the answer: each such copy drifted from the CLI (no seed discovery, no identity injection, a context that defaults the deployment whatever the fixture says).
