# Pack: RDBMS Migration Contract

**Read when:** you touch schema snapshots, the migration ledger, revisions, `migrations { }` config, a migration adapter (Alembic/MikroORM/SQL), rebaseline, or `commit_migration_state`.
**Not for:** startup readiness of the generated service ([runtime-and-deploy.md](./runtime-and-deploy.md)).
**Core map:** [architecture-cheat-sheet.md](../architecture-cheat-sheet.md)

Incremental, language-neutral, UUID-scoped. State lives under `{app_dir}/.datrix/rdbms-migrations/{rdbms_id}/`: `schema.json` (canonical snapshot) and `ledger.json` (ordered revision chain of database-agnostic operations).

- Every `RdbmsConfig` requires `id: UUID` in its `.dcfg`. Revisions are immutable and append-only (`GeneratedFile.retention = "append_only"` protects them from manifest cleanup). Destructive changes are generation errors, with no override.
- State reaches disk only when the whole run succeeds: generators stage commits in the run's `MigrationStateTransaction` (`CodegenContext.migration_state_transaction`) and the last stage, `commit_migration_state`, writes them. A failed, dry, or `--only` run leaves `.datrix/rdbms-migrations/<profile>/` byte-identical.
- **The SQL is rendered once per dialect; an adapter only wraps it.** The `RdbmsMigrationAdapter` protocol (`datrix_codegen_kernel.orchestration.migration_adapter`; Python/Alembic, TypeScript/MikroORM are adapters) is `adapter_id`, `target_language`, `adapter_version`, `wrap_revision(revision, rendered) -> GeneratedFile` and `render_support_files(state)`, plus the statement codec every chain audit reads through (`revision_statements`, `with_revision_statements`). It has no optional capability: nothing in the orchestrator asks an adapter what it supports. Shared-owned migrations use `SharedPaths.rdbms_dir`.
- **One migration path.** Every generation renders migrations through the kernel's `MigrationOrchestrator` revision chain and the target's `RdbmsMigrationAdapter`. `datrix generate` has no separate migration export: `--migrations`, `--allow-destructive` and `--migration-format` are unknown options, `PipelineConfig` carries no migration fields and the pipeline has no migrations stage. `datrix_migration` renders no migration text of its own (it holds the snapshot, diff, policy, ledger and state store), so there is no second type map or DDL emitter to keep in step with the adapters.
- **One chain and one apply lock per `rdbms_id`, carried by consumers.** A shared block's chain is rendered once, in a shared pass before any service (`LanguageGenerator._render_shared_migration_chains`), and every service that `uses` the block receives it byte for byte (`MigrationOrchestrator.render_consumed_shared_block`, a seam comparison that refuses a drifted copy). The chain belongs to the language of the block's chain applier (kernel `shared_chain_ownership`): only that language's generator renders it, and a consumer generated in another language carries no copy and reaches the block through its connection surface. One consumer applies a consumed chain: the block's chain applier, the first consumer by qualified name holding `readwrite` (`shared_chain_applier`; a block every consumer reads is SHR014). It applies before its own blocks, under the advisory lock the block's dialect derives from the `rdbms_id` (`SQLDialect.session_lock_sql`, failing closed on a dialect without one). Every other consumer's migration step, a reader's or another writer's, runs no DDL: it waits, within the same lock budget, until the block's version table records the chain head its image carries. It fails at once on a revision the chain does not hold, and after the budget when the head never arrives (`applies_rdbms_chain` / kernel `awaits_shared_chain`, Python `runtime/chain_head.py`, TypeScript `applyBlockMigrations`). A reader connects with a credential that can only read. Docker gives it a SELECT-only login created by a one-shot reader provision. Azure App Service gives its Entra role CONNECT, USAGE and SELECT plus default SELECT for the applier's role. Azure VM refuses a reader, because every container shares the VM's identity. AWS gives it a SELECT-only login that the shared-infrastructure stack creates with an in-VPC custom resource, connected as the database's master login with full certificate verification; a reader of a shared database AWS does not provision is refused, since no login could be created for it. On every platform the reader's password is a secret of its own: the application secret placement stores it as `<block>_reader_password` and resolves the reader's `<block>_password` to it (`PlacedSecret.read_as`), and the master credential is never re-exported, exposed or granted to a reader. The seed of a shared block runs only in a `readwrite` consumer, inside the chain lock. A consumer allocates no revision and its adapter emits no support files for the shared block. Where a service's migration step runs is one platform fact, `run_migrations_at_startup`, read by every language through the kernel's `service_runs_startup_migrations`. On Docker it runs in a one-shot init container. On Azure App Service and AWS (ECS Fargate, App Runner) it runs in the service process before it serves: Python's `main.py` startup, or TypeScript's `main.ts` before `NestFactory.create`, both calling the block's own apply step. Every applying block, owned or consumed, takes one session lock in its dialect (`apply_lock_for_block`; never a hardcoded `pg_` statement), and the seeds run after under a lock of their own. Each platform sizes every health window that could kill the process meanwhile from `required_service_startup_seconds`, and fails generation when its maximum cannot hold it. Who is a consumer is answered once, by `datrix_common.datrix_model.shared_rdbms_scope` (`realized_rdbms_blocks`, `shared_rdbms_consumers`); per-block access emission walks the realized blocks while schema ownership (DDL, `rdbms_id` validation, provisioning) stays with the owner. SHR007 rejects a write through `readonly` access, including in the lifecycle hooks of a consumed entity, which run in each consumer that writes it. SHR008 rejects an alias collision, SHR009 an unconsumed shared block, and SHR014 a shared block no consumer may apply. A consumed entity's hook may call the shared container's functions and read its constants: each writing consumer realizes the ones its hooks reach, transitively, exactly as it realizes an imported module's (`datrix_common.datrix_model.shared_declarations`). A reader emits no lifecycle hooks.
- A ledger belongs to the language that sealed it (every revision is one language's rendering, replayed verbatim): a second `--language` against it is refused (`guard_foreign_language_ledger`), naming both remedies (`migrations rebaseline --language`, or no ledger).
- **One index set per table.** `datrix_migration.schema_snapshot.entity_table_indexes` is the table's index set -- each declared index over exactly the columns it lists (a `Tenantable` entity too; the trait's `indexed` `tenantId` gives the tenant index), then field-level `: index` and the spatial index a geographic column implies -- recorded by the snapshot and created by the SQL generator's DDL alike.
- **A column's DEFAULT and `: unique` are migrated facts.** The snapshot differ (`compute_snapshot_diff`) emits `FIELD_DEFAULT_CHANGED` / `FIELD_UNIQUE_CHANGED`; every adapter renders them through `datrix_codegen_kernel.sql_facts.snapshot.column_constraint_change` over the kernel dialect (`SET`/`DROP DEFAULT`, a unique constraint added as `uq_<table>_<col>` or dropped by a catalog lookup of the column), the default after every other change (`schema_change_order`). Every table is created with its recorded defaults as database defaults, and a column added later ends up as one created with its table. A ledger recorded below snapshot format 8 has every default re-asserted once (`plan_default_reassertions`). A collection literal default is recorded as the JSON document it declares (`datrix_common.datrix_model.collection_default`), never shortened. Which DDL an engine speaks is one fact, `RdbmsEngine.ddl_dialect` (MariaDB speaks MySQL's), resolved by `get_sql_dialect` and every dialect-keyed table.
- **A column is identified by its column name, never its DSL field name.** The snapshot differ matches a table's fields across two snapshots by `SnapshotColumn.column_name`, so a field renamed only in its DSL spelling (`heightAGL` → `heightAgl`, both `height_agl`) is no change and plans no revision, while a rename that moves the column is a `FIELD_REMOVED` plus a `FIELD_ADDED`. A change still names its field by DSL name: a removed column by the previous snapshot's name, every other change by the current one, the name revisions render against.
- **One schema authority, one index-naming rule.** The snapshot is the only description of the schema a migration renders: no generated migration (the TypeScript baseline included) asks an ORM to diff entity decorators against the database at run time. Every index and unique constraint is named by `datrix_migration.index_naming` (plain `ix_`, declared unique `uq_` as a constraint, fulltext `ix_…_fulltext`, spatial `gist_`; one `truncate_db_identifier` cap) from the entity model, the SQL generator and every adapter alike, and the realized name is recorded in `SnapshotIndex.name` so a drop or rename targets the name the database holds. An index whose recorded name differs from the name it carries now is moved by one generated `INDEX_RENAMED` revision (`plan_index_renames`). One whose snapshot recorded no name is refused with the `datrix migrations rebaseline` remedy, forward and in its rollback alike; the exception is a declared unique, whose rename renders nothing.
- **Foreign keys are created, named once, explicit, and re-asserted.** Every constraint is named by `datrix_migration.foreign_key_naming` (`fk_<table>_<columns>`, the one identifier cap) from the snapshot builder, the SQL generator's DDL and junction tables, and both adapters alike; the realized name is recorded in `SnapshotForeignKey.name` (snapshot format 7) so a drop targets what the database holds. Every baseline creates every key the snapshot records, and an entity added later gets its keys in the same revision (`RELATIONSHIP_ADDED`, matched by the FULL columns / referred table / referred columns tuple through `foreign_key_of_change` -- two keys to one table are ordinary). Every constraint states `ON DELETE` and `ON UPDATE` through `sql_referential_action` (the DSL default is `restrict`; the ORM models state both too, and the TypeScript ORM refuses an action outside the DSL vocabulary). A key whose `onDelete`/`onUpdate` changed, or that a database may hold absent, under an ORM schema generator's name (`<table>_<columns>_foreign`) or under the Python adapter's old `fk_<table>_<columns>_<referred>` name, is re-asserted by one generated `FOREIGN_KEY_REASSERTED` revision (`plan_foreign_key_reassertions`): every candidate name is dropped where it exists, then the key is added under the shared name -- on PostgreSQL `NOT VALID` then `VALIDATE CONSTRAINT`, on MySQL validated on add. An orphan row fails the revision, naming the constraint; no row is deleted. The classification is `risky`. A reflector (`datrix-codegen-sql` `dialects/`) records a live key's action through `dsl_referential_action`, so a reflected and a declared key compare action for action. The SQL generator renders no migration.
- **Every physical table the application uses is in the snapshot, once.** `RdbmsSchemaSnapshot.migration_tables()` is the one set a baseline creates, a relocation moves and the differ reads: entity tables, CQRS read-model tables, audit-log tables and many-to-many junction tables. The audit-log table is declared once (`audit_log_table`; the SQL DDL is rendered from it, each ORM model is compared with it by a test, the trace-id column is always present); a junction table is derived once (`datrix_common.datrix_model.junction.junction_tables`: sorted-pair name, owning side, composite key, named `CASCADE` keys, reverse index) for the snapshot, the SQL DDL and every ORM's join table alike, and an entity related to itself is refused by name. A CQRS view model declares exactly the table-level index and unique rows the snapshot records for its table (never a column-level `index` flag; a column named only in a composite or unique row is not indexed on its own).
- **A change to an existing enum type is realized on every engine.** Appending a member and relabeling one are rendered by the kernel from `datrix_codegen_kernel.sql_facts.enum_member_change` and the dialect (`render_add_enum_value`, `render_rename_enum_value`): PostgreSQL through `ALTER TYPE … ADD VALUE` / guarded `RENAME VALUE`; MySQL/MariaDB (labels inline in each column's type) by restating every column typed with the enum with `MODIFY COLUMN` carrying its whole definition -- a relabel widens, moves the rows with one `UPDATE … CASE`, then narrows. An append has no automatic rollback on any engine; a removal or a reorder is a blocked (destructive) change. A builtin call default (`= uuid()`, `= DateTime.now()`) is recorded as a `server_function` default, never a `literal`; every other default is a stored value recorded as a `literal`, on a `server` field too (`ScheduleStatus status : server = ScheduleStatus.Pending`, `Int version : server = 1`). A ledger snapshot sealed under older rules is read under today's kinds (`datrix_migration.schema_snapshot.read_recorded_default`) wherever a recorded default is compared or stated, so a rollback restates such a value as the value it is.
- **A whole revision renders once, in the kernel.** `datrix_codegen_kernel.sql_facts.revision.render_revision(state, revision, dialect)` returns a `RenderedRevision`: an ordered tuple of `SqlStatement`s, each carrying its `SqlStatementKind` (a closed set), the object it is about and its SQL. A baseline runs the schema prelude (`render_create_schema`, `render_set_search_path` where the dialect `supports_feature("schema_namespaces")`), the named enum types (`named_enum_types`), every table, every foreign key (validated: the tables are empty), every index and column unique, then the comments the dialect keeps out of `CREATE TABLE`. An incremental revision runs the search-path prelude, then its changes in `schema_change_order`. Statements are unqualified; the schema is reached through the search path. Every `ChangeKind` is either rendered (`CHANGE_KIND_STATEMENT_KINDS`, the statement kinds it may produce, checked on every rendering) or refused with its reason (`REFUSED_CHANGE_KINDS`: a removed or reordered enum label); the two sets partition `ChangeKind`. A removal reads the previous snapshot, an addition the current one. An `INDEX_ADDED` carrying the repair marker is created only where absent: a constraint or fulltext/spatial index with `IF NOT EXISTS`, a plain index only on a dialect with `guarded_index_creation`, any other dialect refusing it (`DialectFeatureError`). An `INDEX_RENAMED` with no recorded old name of a plain index is refused, naming `datrix migrations rebaseline`: the kernel holds no name the database could carry. The orchestrator renders each allocated revision once, for every language, through `datrix_codegen_kernel.orchestration.migration_render.render_migration_revision`. `render_revision_once` renders the forward statements and their rollback (a `RevisionRendering`). It refuses an incremental over an empty diff, and any change outside `NON_DESTRUCTIVE_CHANGE_KINDS` (`require_incremental_operations`). The adapter's `wrap_revision` wraps that rendering in one file. The kernel then reads the file back through the adapter's own codec and refuses it unless it runs exactly the rendered statements, in order, and is append-only. It builds the revision's manifest artifact from the file and returns the statement descriptors the ledger records. The same path renders the single-baseline refresh, the automatic rebaseline and `datrix migrations rebaseline`. Every adapter's forward revision is this statement list and nothing else: Alembic's `upgrade()` is one `op.execute(sa.text(...))` per statement (each escaped once by `escape_for_sa_text`, plus a `STATEMENTS` table of `(kind, object kind, name, table)` rows), MikroORM's `up()` the same statements. Every rollback is composed once, by `datrix_codegen_kernel.sql_facts.revision_rollback` (a baseline drops what it created; an incremental undoes each change last first through its undo kind over the swapped snapshots); only the wording of a refused rollback is the target's.
- **The ledger records each revision's statements (ledger v5).** Every appended `RevisionRecord` carries `statements`: one `StatementDescriptor` per statement of the kernel's `render_revision` -- kind, object kind, object name, table and the SHA-256 of the SQL, never the SQL or a credential. The descriptors come from the same rendering the adapter wrapped (`render_migration_revision`); a rebaseline (CLI or the generation-time automatic one) records the fresh baseline's on its head (`record_head_statements`); an `adopted` revision records `[]`. A record without descriptors -- every pre-v5 record, a revision renaming an index from a name no snapshot recorded, a `reconcile --to-desired` revision -- is unreadable (`revisions_without_descriptors`): an audit over the chain refuses over it, never passes, and `datrix migrations rebaseline` clears it (its builder never reports a no-op while one remains). v1–v5 ledgers stay readable and reserialize byte for byte.
- **A long-lived database's unreadable chain is carried forward, not reset (ledger v6).** `datrix migrations rebaseline` rests on exactly one stated premise. `--assume-wiped` resets (R := D, `build_rebaselined_state`; refused in guard mode). `--rdbms-id <id> --live-snapshot <file>` carries forward (R := R, `build_carried_forward_state`; permitted in every mode, guard included, since it resets nothing): the exported live schema must equal the recorded schema, the fresh baseline builds exactly that schema under a new id, and `rebaselined_from.carried_revision` names the chain's last revision with a revision file -- the retired id a proven database records (an `adopted` record after it has no file and ran nothing). `validate_ledger` accepts a carried revision only from v6 on and only as one of the provenance's superseded ids. The kernel hands it to the adapter as `MigrationChainProvenance.carried_revision` (`build_chain_provenance`), and each language's generated runner moves a history whose latest recorded revision is the carried one onto the baseline without DDL, under the apply lock; every other retired history stays refused. Alembic declares it in env.py (`CARRIED_REVISION`); MikroORM records migrations by file name, so the TypeScript adapter writes the carried file-name prefix onto the carried baseline's class (`carriedMigrationPrefix`, from `revision_sequence` -- every allocator formats an id as its zero-padded sequence and a slug), which `migration-history.ts` reads. A shared block's waiting consumer waits for the applier's move. The chain audit's refusal names `--live-snapshot` for a live database and `--assume-wiped` for a disposable one (`unverifiable_chain_message`).
- **Every language's stored chain is audited before a generation renders over it.** The orchestrator's audit step (`datrix_codegen_kernel.orchestration.migration_chain_replay.repair_unapplicable_chain`, over `migration_audits`) runs for every adapter. No adapter opts in or out. Each revision file's statements are read back through the adapter's required `revision_statements` and must match the record's descriptors by count and SHA-256. An undescribed record, an unreadable file or an edited statement refuses with the rebaseline remedy (`unverifiable_chain_message`). The verified descriptors are then replayed from an empty catalog: tables, indexes and constraints per table, and enum types. That replay reports a creation of an object the chain already holds, or a use of a table, index or enum type no earlier revision created, at its statement position. Guardedness and a rename's old name are read back from the SQL by the block's dialect. A duplicate the dialect can guard (`guarded_creation`) is rewritten at exactly that position through the adapter's `with_revision_statements`, and its SHA-256 is re-recorded on the sealed record (`rerecord_statement_hashes`), committed with the file. The permission rests on end-state identity: the guarded statement leaves a database that already holds the object exactly as the original did. Every other defect refuses (`guard_unapplicable_chain`).
- **Every chain audit runs in the orchestrator, for every language.** The verified replay's end state (`migration_audits.chain_end_state`, computed once per generation) feeds three audits. The first is the enum labels the chain holds (`enum_labels_held_by_chain`, read back from the SQL by the dialect's `enum_label_change`; MySQL/MariaDB hold labels inline and read none). They correct the recorded snapshot's claim before the diff is planned (`reconcile_recorded_enum_labels`). The second is the declared indexes no revision created (`uncreated_indexes`), which get a guarded repair addition. The third is the planned additions of an index the chain already creates (`already_created_index_additions`), which are marked as repairs (`guard_redundant_index_additions`). A rewrite of a sealed sole baseline (`refresh_stale_single_baseline`) is permitted when its forward statements still hash to the record's descriptors, in order (`applied_path_unchanged`): the database it built is the one the rewrite builds. Every incremental passes `require_incremental_operations` before it renders. Each audit fails closed: an undescribed record or an unreadable file refuses with the rebaseline remedy, never passes.
- `fulltext(...)` is realized on PostgreSQL only: a GIN index over the shared coalesce `to_tsvector` expression, which both languages' query step repeats verbatim. Any other engine is a generation error (`datrix_codegen_kernel.algorithms.fulltext_dialect`), never a differently-behaving index.
- `migrations { enabled; ledger }` per profile, both default on. `ledger = false` runs stateless (fresh baseline every generation, nothing under `.datrix/`); every reference example declares it, and the parity gate fails a run that leaves a ledger behind.
