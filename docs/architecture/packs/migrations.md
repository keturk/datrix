# Pack: RDBMS Migration Contract

**Read when:** you touch schema snapshots, the schema converge, `migrations { }` config, or the kernel's schema rendering.
**Not for:** startup readiness of the generated service ([runtime-and-deploy.md](./runtime-and-deploy.md)).
**Core map:** [architecture-cheat-sheet.md](../architecture-cheat-sheet.md)

Language-neutral, UUID-scoped. Every deploy converges each block's live catalog to its declared schema: `schema.json`, the canonical snapshot generation writes into the block's schema tool. No migration history, revision chain or generator state is kept.

- Every `RdbmsConfig` requires `id: UUID` in its `.dcfg`. A destructive change runs only with the deploy's `--approved` switch, and some changes are never applied (`datrix-migration/docs/architecture.md` § Convergence outcomes).
- **The SQL is rendered once per dialect, by the kernel.** No language plugin declares a migration adapter (`LanguagePlugin` has no such member), and the deploy's schema client applies every schema.
- **One migration path.** The deploy's schema converge builds and changes every block's schema (`converge_schema_blocks`). `datrix generate` renders no migration: `--migrations`, `--allow-destructive`, `--migration-format` and `--carry-forward-live-snapshots` are unknown options, `PipelineConfig` carries no migration fields, the pipeline has no migrations stage and no `datrix migrations` command exists. `datrix_migration` renders no migration text of its own (it holds the snapshot, diff, policy and convergence planner), so there is no second type map or DDL emitter to keep in step with the kernel.
- **One schema and one apply lock per `rdbms_id`, converged once by the deploy.** No generated service migrates its database or holds a DDL credential, on any platform or in any language: the deploy's schema client converges every block (`converge_schema_blocks`) and alone reads the block's owner login. A shared block is converged once, under the advisory lock the block's dialect derives from the `rdbms_id` (`SQLDialect.session_lock_sql`, failing closed on a dialect without one). The block's chain applier, the first consumer by qualified name holding `readwrite` (`shared_chain_applier`; a block every consumer reads is SHR014), only names the block's owner. Every consumer, a reader or a writer, connects as a service or reader login of its own, which holds data rights and no DDL right, and none waits for or applies a chain. A reader connects with a credential that can only read. Docker gives it a SELECT-only login created by a one-shot reader provision. Azure App Service gives its Entra role CONNECT, USAGE and SELECT plus default SELECT for the applier's role. Azure VM refuses a reader, because every container shares the VM's identity. AWS gives it a SELECT-only login that the stack provisioning the database creates with an in-VPC custom resource realizing the database's access plan, connected as the database's master login (the plan's owner) with full certificate verification; a reader of a shared database AWS does not provision is refused, since no login could be created for it. On every platform a login's password is a secret of its own: the application secret placement stores it as `<login>_password` and resolves the holder's `<block>_password` to it (`PlacedSecret.read_as`), and the master credential is never re-exported, exposed or granted to a reader. The seed of a shared block runs only in a `readwrite` consumer, inside the block's session lock. Whether a service seeds in its own process at startup is one platform fact, `run_seeds_at_startup`, read by every language through the kernel's `service_runs_startup_seeds_in_process`; the seed takes the block's session lock in its dialect (never a hardcoded `pg_` statement), and no platform runs a migration container, task or in-process step. The platform's health windows render their configured values. Who is a consumer is answered once, by `datrix_common.datrix_model.shared_rdbms_scope` (`realized_rdbms_blocks`, `shared_rdbms_consumers`); per-block access emission walks the realized blocks while schema ownership (DDL, `rdbms_id` validation, provisioning) stays with the owner. SHR007 rejects a write through `readonly` access, including in the lifecycle hooks of a consumed entity, which run in each consumer that writes it. SHR008 rejects an alias collision, SHR009 an unconsumed shared block, and SHR014 a shared block no consumer may apply. A consumed entity's hook may call the shared container's functions and read its constants: each writing consumer realizes the ones its hooks reach, transitively, exactly as it realizes an imported module's (`datrix_common.datrix_model.shared_declarations`). A reader emits no lifecycle hooks.
- **One index set per table.** `datrix_migration.schema_snapshot.entity_table_indexes` is the table's index set -- each declared index over exactly the columns it lists (a `Tenantable` entity too; the trait's `indexed` `tenantId` gives the tenant index), then field-level `: index` and the spatial index a geographic column implies -- recorded by the snapshot and created by the SQL generator's DDL alike.
- **A column's DEFAULT and `: unique` are migrated facts.** The snapshot differ (`compute_snapshot_diff`) emits `FIELD_DEFAULT_CHANGED` / `FIELD_UNIQUE_CHANGED`; the kernel renders them through `datrix_codegen_kernel.sql_facts.snapshot.column_constraint_change` over the kernel dialect (`SET`/`DROP DEFAULT`, a unique constraint added as `uq_<table>_<col>` or dropped by a catalog lookup of the column), the default after every other change (`schema_change_order`). Every table is created with its recorded defaults as database defaults, and a column added later ends up as one created with its table. A collection literal default is recorded as the JSON document it declares (`datrix_common.datrix_model.collection_default`), never shortened. Which DDL an engine speaks is one fact, `RdbmsEngine.ddl_dialect`, resolved by `get_sql_dialect` and every dialect-keyed table.
- **A column is identified by its column name, never its DSL field name.** The snapshot differ matches a table's fields across two snapshots by `SnapshotColumn.column_name`, so a field renamed only in its DSL spelling (`heightAGL` → `heightAgl`, both `height_agl`) is no change, while a rename that moves the column is a `FIELD_REMOVED` plus a `FIELD_ADDED`. `snapshots_describe_the_same_schema` compares columns by the same identity. A change still names its field by DSL name: a removed column by the previous snapshot's name, every other change by the current one.
- **One schema authority, one index-naming rule.** The snapshot is the only description of the schema a migration renders: no generated migration (the TypeScript baseline included) asks an ORM to diff entity decorators against the database at run time. Every index and unique constraint is named by `datrix_migration.index_naming` (plain `ix_`, declared unique `uq_` as a constraint, fulltext `ix_…_fulltext`, spatial `gist_`; one `truncate_db_identifier` cap) from the entity model, the SQL generator and the kernel's renderer alike, and the realized name is recorded in `SnapshotIndex.name` so a drop or rename targets the name the database holds. An index whose recorded name differs from the name it carries now is moved by one generated `INDEX_RENAMED` revision (`plan_index_renames`). One whose snapshot recorded no name is refused, forward and in its rollback alike; the exception is a declared unique, whose rename renders nothing.
- **Foreign keys are created, named once, explicit, and re-asserted.** Every constraint is named by `datrix_migration.foreign_key_naming` (`fk_<table>_<columns>`, the one identifier cap) from the snapshot builder, the SQL generator's DDL and junction tables, and both adapters alike; the realized name is recorded in `SnapshotForeignKey.name` (snapshot format 7) so a drop targets what the database holds. Every baseline creates every key the snapshot records, and an entity added later gets its keys in the same revision (`RELATIONSHIP_ADDED`, matched by the FULL columns / referred table / referred columns tuple through `foreign_key_of_change` -- two keys to one table are ordinary). Every constraint states `ON DELETE` and `ON UPDATE` through `sql_referential_action` (the DSL default is `restrict`; the ORM models state both too, and the TypeScript ORM refuses an action outside the DSL vocabulary). A key whose `onDelete`/`onUpdate` changed, or that a database may hold absent, under an ORM schema generator's name (`<table>_<columns>_foreign`) or under the Python adapter's old `fk_<table>_<columns>_<referred>` name, is re-asserted by one generated `FOREIGN_KEY_REASSERTED` revision (`plan_foreign_key_reassertions`): every candidate name is dropped where it exists, then the key is added under the shared name -- on PostgreSQL `NOT VALID` then `VALIDATE CONSTRAINT`. An orphan row fails the revision, naming the constraint; no row is deleted. The classification is `risky`. A reflector (`datrix-codegen-sql` `dialects/`) records a live key's action through `dsl_referential_action`, so a reflected and a declared key compare action for action. The SQL generator renders no migration.
- **Every physical table the application uses is in the snapshot, once.** `RdbmsSchemaSnapshot.migration_tables()` is the one set a baseline creates, a relocation moves and the differ reads: entity tables, CQRS read-model tables, audit-log tables and many-to-many junction tables. The audit-log table is declared once (`audit_log_table`; the SQL DDL is rendered from it, each ORM model is compared with it by a test, the trace-id column is always present); a junction table is derived once (`datrix_common.datrix_model.junction.junction_tables`: sorted-pair name, owning side, composite key, named `CASCADE` keys, reverse index) for the snapshot, the SQL DDL and every ORM's join table alike, and an entity related to itself is refused by name. A CQRS view model declares exactly the table-level index and unique rows the snapshot records for its table (never a column-level `index` flag; a column named only in a composite or unique row is not indexed on its own).
- **A change to an existing enum type is realized on every engine.** Appending a member and relabeling one are rendered by the kernel from `datrix_codegen_kernel.sql_facts.enum_member_change` and the dialect (`render_add_enum_value`, `render_rename_enum_value`): PostgreSQL through `ALTER TYPE … ADD VALUE` / guarded `RENAME VALUE`. An append has no automatic rollback on any engine; a removal or a reorder is a blocked (destructive) change. A builtin call default (`= uuid()`, `= DateTime.now()`) is recorded as a `server_function` default, never a `literal`; every other default is a stored value recorded as a `literal`, on a `server` field too (`ScheduleStatus status : server = ScheduleStatus.Pending`, `Int version : server = 1`). Every default but a collection literal also records the SQL tree it lowers to (`SnapshotDefault.tree`), excluded from equality. Every statement stating a default renders it from the tree the desired snapshot records; a default without one is refused, never spelled from its text. A snapshot of any format version but `SCHEMA_VERSION` is refused with the instruction to regenerate it.
- **A block's SQL renders once, in the kernel.** `datrix_codegen_kernel.sql_facts.revision` returns a `RenderedRevision`: an ordered tuple of `SqlStatement`s, each carrying its `SqlStatementKind` (a closed set), the object it is about and its SQL. `render_schema(snapshot, dialect)` renders a whole schema from empty: the schema prelude (`render_create_schema`, `render_set_search_path` where the dialect `supports_feature("schema_namespaces")`), the named enum types (`named_enum_types`), every table, every foreign key (validated: the tables are empty), every check constraint, every index and column unique, the comments the dialect keeps out of `CREATE TABLE`, then the table triggers. `render_convergence(live, desired, changes, dialect)` renders the changes that bring a live catalog `L` to the declared schema `D`, behind the search-path prelude, in `schema_change_order`, with no whole-schema path: removals read from `L` under the names the database holds, additions from `D`, and `create_schema` in the prelude when `L` holds no table and no enum type (a catalog reader stamps the block's place on what it reads, so a schema the database lacks reads as one holding nothing; the dialect creates a schema only where it is absent) or the changes relocate the block into it. An empty catalog therefore renders the prelude and then all of `D`. Statements are unqualified; the schema is reached through the search path. Every `ChangeKind` is either rendered (`CHANGE_KIND_STATEMENT_KINDS`, the statement kinds it may produce, checked on every rendering) or refused with its reason (`REFUSED_CHANGE_KINDS`: a removed or reordered enum label); the two sets partition `ChangeKind`. A check (`ADD_CHECK_CONSTRAINT` for a schema's check or a `CHECK_ADDED`, `DROP_CHECK_CONSTRAINT` for a `CHECK_REMOVED`) is written from the lowered tree the snapshot records, by `datrix_migration.sql_lowering.render.render_sql` for the block's DDL dialect, through the dialect's `render_add_check_constraint` / `render_drop_check_constraint`; a check with no tree (one a live catalog reflected) is refused when it would be created, and one whose SQL's digest is not the one its name ends in is refused, since its name no longer identifies its definition. A drop needs the name only. An `INDEX_RENAMED` renames the index `L` holds under the change's old name; an old name `L` does not hold is refused.
- `fulltext(...)` is realized on PostgreSQL only: a GIN index over the shared coalesce `to_tsvector` expression, which both languages' query step repeats verbatim. Any other engine is a generation error (`datrix_codegen_kernel.algorithms.fulltext_dialect`), never a differently-behaving index.
- `migrations { enabled }` per profile, default on: `false` leaves every RDBMS block of the profile out of the deploy's schema converge. Any other key in the block, and a `driftPolicy` section, is refused when the config loads.
