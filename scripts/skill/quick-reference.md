# Skill Scripts Quick Reference

Scripts that exist for the agent skills under `.claude/skills/`: running skills as headless steps on their own models, and the mechanical skill phases done by a script or a local model. Each `.ps1` is rendered from the shared entrypoint template and runs a module of `common/lib/datrix_scripts/skill/`; each has a POSIX twin `.sh` beside it taking the same options as `--kebab` flags.

## Headless skill chains: `skill\implement-design.ps1`, `skill\skill-chain.ps1`

**Run skills one after another as headless `claude -p` steps, each on its own skill's `model:`/`effort:`.** A skill invoked from inside another skill runs on the caller's model; a typed slash command switches to the skill's own. Each step here is a typed slash command in its own run, with the workspace's hooks, CLAUDE.md and guards. The shared step runner is `datrix_scripts.skill.chain`. It types each prompt into the step's `claude -p` run on stdin, never as an argument (the `claude.cmd` shim is a batch file, and cmd.exe ends an argument at its first newline), refuses an argument cmd.exe would reinterpret, and validates the model, effort, permission mode and session id before launching. It starts every step with `CLAUDE_CODE_AUTO_COMPACT_WINDOW=500000`, so a long step compacts at 500k tokens instead of growing toward the model's 1M window: each response re-reads the whole context, so the context size sets what a long step costs (the caller's own value comes back after the step). Interactive sessions get the same window from `"autoCompactWindow": 500000` in the workspace `.claude/settings.json`; the variable, when set, takes precedence over it. Needs the workspace trusted in `~/.claude.json` (`hasTrustDialogAccepted`), or headless runs ignore `settings.json`'s permissions.

| Mode | Command | Description |
|------|---------|-------------|
| **Implement a design** | `.\skill\implement-design.ps1 -Design "D:\datrix\design\<file>.md"` | `/implement-design-direct` as a `STOP AFTER: plan` session, one `UNIT: <id>` session per ledger unit, and a `UNIT: sweep` session → verify → absorb |
| **Resume it after a question** | `.\skill\implement-design.ps1 -Design "<file>" -StartAt verify` | Start at `implement`, `verify` or `absorb` (after `implement`, its ledger must exist) |
| **Any sequence** | `.\skill\skill-chain.ps1 "/fix-codegen-python <index.json>" "/commit-and-push"` | Prompts in order; stops at the first error |
| **One session throughout** | append `-Resume` | Carry one session through every step instead of a fresh one per step |
| **Preview** | append `-DryRun` | Print the steps; run none |
| **Summary lines only** | append `-Quiet` | By default each agent message, tool call and refused tool call is printed as it happens; `-Quiet` shows only each step's prompt and summary |

`implement-design.ps1` checks the result between steps itself; no model decides it:
- The implement step keeps its ledger at `D:\datrix\.tmp\implement-direct-<design file name>.md`. The plan session runs only when there is no ledger (or verify left gaps); no ledger after it means it stopped at its gate for a decision. Each unchecked unit then runs in its own fresh session (up to `-MaxRounds` per unit), because every response re-reads the whole context: one session over all units of a 7-unit design averaged 270k tokens per response and compacted twice. Implement sessions run with `--tools` limited to Bash, Read, Edit, Write, Grep, Glob, Skill, ToolSearch and Task, and with only the workspace `.mcp.json` servers (`--strict-mcp-config`): that start-up context is 34k tokens, against 56k with all 50 tools. The step is done only when the sweep session leaves a ledger with no unchecked unit and a `## Files changed` section.
- Absorb runs only after verify replies `Design conformance: PROVEN`. The verdict is read from every reply of the verify session's transcript, not only the last (a Stop hook that refuses a reply makes the session send another), and `.claude/checklists/verify-verdict.json` refuses a `/verify-implementation` turn that ends without the line. On INCOMPLETE, implement runs again with `GAPS:` set to verify's saved report, then verify. On PROVEN, verify's replies are kept at `D:\datrix\.tmp\verify-proven-<design file name>.md` and passed to `/absorb-design` as `VERIFIED:`, its licence to delete the design whatever the design's own `Status:` line says; `-StartAt absorb` stops with exit 1 when that file is missing or not PROVEN. Without `-KeepSource`, absorb must have deleted the design; otherwise it stopped at a question.

**Fresh vs `-Resume`.** A fresh step pays the workspace start-up context (about 52k tokens measured on an implement session: system prompt, tools, skill list, CLAUDE.md and the skill itself, mostly served from the prompt cache when the model repeats) plus the mandatory reads, and starts with its context window free. `-Resume` re-reads nothing, but every turn of every step re-reads all previous steps' transcript, and on a model change that whole transcript is written to the cache again at the new model's price. The design steps hand over through files (ledger, reports), so fresh is the default.

**From Git Bash**, set `MSYS_NO_PATHCONV=1` for `skill-chain.ps1`, or a leading `/` in a prompt is rewritten into a Windows path.

**Parameters:** `-Design` (or the first positional argument), `-StartAt`, `-KeepSource`, `-MaxRounds` (default 3) for `implement-design.ps1`; the prompts as positional arguments for `skill-chain.ps1`. Both: `-Resume`; `-PermissionMode auto|acceptEdits|dontAsk|bypassPermissions` (default `auto`; the guards run in every mode); `-MaxBudgetUsd` (per step, list price); `-DryRun`; `-Quiet`. Logs: `D:\datrix\.tmp\skill-chain\<timestamp>\` (each step's result `.json`, every streamed event `.stream.jsonl`, stderr, and each INCOMPLETE verify report). **Exit codes:** 0 done; 1 a step ended in error or a check failed; 2 a step stopped for a decision only Jon can make (its reply and session id are printed), or a command line the module cannot read.

**Modules:** `datrix_scripts.skill.implement_design`, `datrix_scripts.skill.skill_chain`; POSIX twins `skill/implement-design.sh` (`--design`, `--start-at`, `--keep-source`, `--resume`, `--permission-mode`, `--max-budget-usd`, `--max-rounds`, `--dry-run`, `--quiet`, `--self-test`) and `skill/skill-chain.sh` (the prompts as positionals or repeated `--step`, `--resume`, `--permission-mode`, `--max-budget-usd`, `--dry-run`, `--quiet`, `--self-test`). `-SelfTest` runs the chain checks (stdin delivery, refused arguments, the kept and shown stream, session replies, absorb refused without a proof, a dry run) and the wrapper seam checks.

## `skill\implement-finding.ps1`

**Drain the findings inbox one finding at a time: one session per finding, closed before the next starts.** The multi-finding form of `/implement-finding`. Per finding, in name order, one fresh headless `/implement-finding` session (via `datrix_scripts.skill.chain`, started with `--model`/`--effort`) checks the finding against the code and, when it still holds, fixes it (code, tagged test, targeted runs, docs, pointers from other findings). It ends `Finding fix: ALREADY RESOLVED`, `DONE` or `BLOCKED B<n>` and never deletes the finding itself. The script then runs `finding-close`: never while another findings file names the finding, and after `DONE` only when the session's last foreground `test.ps1` or `*-gate.ps1` run passed (a gate proves code no `test.ps1` reaches, such as the scripts tree), read from the step's `.stream.jsonl` — not a model's word.

| Mode | Command | Description |
|------|---------|-------------|
| **First 10 findings** | `.\skill\implement-finding.ps1` | One session each, on Opus, from the first inbox subfolder (area order: `python`, `typescript`, … `docs`, then other subfolders by name), going on to the next subfolder once the one before holds no more, and last the files lying directly in `reports\finding` |
| **Fewer** | `.\skill\implement-finding.ps1 -Count 3` | The first 3 by name |
| **One folder** | `.\skill\implement-finding.ps1 azure` (or `-Dir azure`, or a full path such as `D:\datrix\reports\finding\python`) | Only that subfolder (absolute, or relative to `reports\finding`) |
| **Given files** | `.\skill\implement-finding.ps1 -Finding "D:\datrix\reports\finding\<file>.md"` | Instead of the first `-Count`; worked as given, wherever they are |
| **Preview** | append `-DryRun` | List the findings and print the steps; run none |

**Parameters:** `-Count` (default 10), `-Finding`, `-Dir` (one folder, absolute or relative to `<workspace>\reports\finding`; default: the subfolders in turn), `-Model` (default `claude-opus-5-5`), `-Effort` (default `high`), `-PermissionMode`, `-MaxBudgetUsd`, `-DryRun`, `-Quiet`. Step logs: `D:\datrix\.tmp\skill-chain\<timestamp>\`. A session ending `Finding fix: BLOCKED B<n>` stops that finding and the chain moves to the next. **Exit codes:** 0 every finding deleted; 1 a session erred, replied with no outcome line, or a finding was left in place; 2 no failure, but a session stopped for a decision only Jon can make.

The selection and the close run in-process through `datrix_scripts.skill.finding_inbox`, the code behind the `skill-assist.ps1` commands `finding-select` and `finding-close` (below); `/implement-finding` typed by hand calls `finding-close` itself.

**Module:** `datrix_scripts.skill.implement_finding`; POSIX twin `skill/implement-finding.sh` (`--count`, `--finding`, `--dir`, `--model`, `--effort`, `--permission-mode`, `--max-budget-usd`, `--dry-run`, `--quiet`, `--self-test`).

## `skill\organize-findings.ps1`

**Sort the findings files lying directly in the findings folder into one level of area subfolders, by file name alone.** A name in the merged scheme (`NNNN-<area>-<slug>.md`) carries its area; any other name is read by the first word of its slug (an area name or alias such as `azure-`, `ts-`, `gate-`). A name that states no area is sent, by name only, to a local model that picks one of the areas of `/merge-findings` (`python`, `typescript`, `clients`, `language`, `migration`, `seed`, `kernel`, `docker`, `aws`, `azure`, `component`, `tests`, `tooling`, `docs`; each the subject the finding is about, not the package its fix lands in, so the folders can be worked in priority order); its answer is checked against the asked names and the area set, and a name carrying a registered customer term is not sent. File content is never read. Only `*.md` directly in the folder move; nothing inside a subfolder is touched, so there is exactly one level, and a move never overwrites. `finding-select`, `finding-close` and `implement-finding.ps1` work the area subfolders in turn, or one with `-Dir`; the merge and consolidate commands (`findings-*`) still read the one folder they are given.

| Mode | Command | Description |
|------|---------|-------------|
| **Sort the inbox** | `.\skill\organize-findings.ps1` | Move every loose finding into its area folder |
| **Preview** | append `-DryRun` | Print the moves; make none |
| **Names only** | append `-NoModel` | A name that states no area stays where it is |
| **Another folder** | `-Dir "<folder>"` | Default `<workspace>\reports\finding` |

**Parameters:** `-Dir`, `-DryRun`, `-NoModel`, `-LocalMachines`, `-LlmModel`, `-LlmTimeout` (seconds, default 300), `-SelfTest`. **Exit codes:** 0 every file sorted; 1 the folder cannot be read or a move failed; 2 some files stayed (withheld name, no valid model answer); 3 a model was needed and none answered.

**Module:** `datrix_scripts.skill.organize_findings`; POSIX twin `skill/organize-findings.sh` (`--dir`, `--dry-run`, `--no-model`, `--local-machines`, `--llm-model`, `--llm-timeout`, `--self-test`).

## `skill\skill-assist.ps1`

**The mechanical phases of agent skills, done by a script or a local model instead of a Claude model.** Each command writes its output to `d:\datrix\.tmp\assist\` and prints the path with a one-line summary. Exact checks are exact; whatever a local model writes is checked against its inputs (citations and quotes against what it was sent, set comparisons against the source) and is marked as a lead. The skill keeps every verdict. **Module:** `datrix_scripts.skill.skill_assist`, with the commands in the modules of `common/lib/datrix_scripts/skill/`; POSIX twin `skill/skill-assist.sh` (the command, its arguments, `--local-machines`, `--llm-model`, `--llm-timeout`, `--self-test`).

**What is sent to a model.** `findings-redundant` sends both files of each candidate pair whole (a theme file's one section), with the same customer-term filtering. `design-verify` and `design-plan` send each section's title and opening lines (and `design-verify` the cited framework-repo files); like `checklist`, `absorb-transfer`, `findings-index` and `findings-plan` (each unit's title and opening lines) they send design docs and findings files, which the MCP tools refuse; `readiness` and `absorb-transfer` read framework-repo files through the MCP tools' own scope. Every line is checked against the customer-term corpus first and withheld when it carries a registered term; without the corpus nothing is sent. `bug-resolution` sends a diff only for a framework repository, and never one that carries a term.

**Parameters:** the command, then its own python-style arguments; for the model commands the shared local-model flags `-LocalMachines`, `-LlmModel`, `-LlmTimeout` (seconds, default 600). With no `-LlmModel`, `readiness`, `findings-redundant`, `findings-plan`, `absorb-transfer`, `bug-resolution` and `design-plan` use `nemotron-3-super:120b`, then `qwen3-coder:30b-ctx32k` (`QUALITY_MODEL_PREFERENCE`): quality outranks speed there, so they wait for the most capable machine. Measured: `absorb-transfer` on sections known to be absent from the target said PRESENT on `qwen3-coder` for 7 of 7 and MISSING on nemotron for 7 of 7, so it must use nemotron; the other four are in the set by the capability rule and have not been compared. The other model commands (`checklist`, `design-verify`, `findings-index`, `rule-names`) take any resident model: `checklist` (6 designs) and `design-verify` (22 sections) ran 4.7 to 5x slower on nemotron with no better result (`checklist`: 15 unverifiable citations against 6; `design-verify`: 20 of 22 verdicts identical, and nemotron's other two were empty UNCLEARs).

**Exit codes:** 0 done; 1 the request could not be carried out; 2 the check found something to act on (`findings-check` FAIL, `finding-close` kept the finding, `absorb-transfer` partial/missing, `absorb-references` found lines, `absorb-delete` kept the design); 3 no local model answered — do that phase yourself, as the skill did before the assist.

## `skill\skill-assist-gate.ps1`

**The gate for the skill assists:** every assist module of `common/lib/datrix_scripts/skill/` and the `skill-assist.ps1` command line, checked against real files and a stand-in local model server, with no network model. Run it after changing an assist module. **Module:** `datrix_scripts.skill.skill_assist_gate`; POSIX twin `skill/skill-assist-gate.sh` (`--only`, `--harness-self-test`, `--self-test`, `--dbg`).

| Mode | Command |
|------|---------|
| **Run every check** | `.\skill\skill-assist-gate.ps1` |
| **One check** | `.\skill\skill-assist-gate.ps1 -Only <check name>` |
